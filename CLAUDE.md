
# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

ConnectOnion Desktop is a native Windows client (WinUI 3, C#, .NET 10) for chatting with ConnectOnion-compatible agents over WebSocket. The repo is C#-only: the legacy Electron + React `frontend/` and the vendored Python `agent/` examples were both deleted in `197a88d`, so any doc still pointing at them is stale — read them out of git history if you need the prior UX behavior, and don't reintroduce those trees.

Prose docs live in `docs/` (see `docs/README.md`): the wire protocol (`SESSION_MESSAGE_STRUCTURE.md`), the test plan and backlog (`TEST_PLAN.md`), the requirements brief, engineering optimization notes (`OPTIMIZATION.md`), and a historical record of the Electron → WinUI migration. **This file is the authoritative description of the architecture — where a document in `docs/` disagrees with it, this one is right.**

## Solution Layout

Production projects sit at the repo root; every test project lives under `tests/`. All but one are wired into the `.sln` — keep this in mind when running `dotnet build`/`dotnet test` against the solution vs. a project directly:

| Project | In `.sln`? | In CI? | Purpose |
|---|---|---|---|
| `ConnectOnion.WinUIClient/` | yes | build | The WinUI 3 app: XAML, code-behind, and the services that need a window or the Windows App SDK (`net10.0-windows10.0.19041.0`) |
| `ConnectOnion.WinUIClient.Core/` | yes | via tests | **Every WinUI-free surface of the client**: models, SQLite repositories, notification policy, projections, view models. Targets `net10.0-windows10.0.19041.0` but takes no `Microsoft.UI` dependency, so a headless test host can load it |
| `ConnectOnion.Protocol/` | yes | build | Transport-agnostic protocol library (`net10.0`, no WinUI dependency) |
| `ConnectOnion.Protocol.Conformance/` | yes | yes | Cross-checks C# Ed25519/canonical-JSON signing against a Node.js reference signer (`ref-sign.js`) — this is the CI gate |
| `ConnectOnion.Protocol.LiveTest/` | no | no | Console script for a real end-to-end run against a deployed agent; run directly with `dotnet run` |
| `tests/ConnectOnion.TrimSmoke/` | no | opt-in | Console harness published **trimmed** that asserts the serialization, persistence and identity paths still work when `JsonSerializerIsReflectionEnabledByDefault` is off. Not xunit — a trimmed self-contained publish has no test host to load into. Run via `scripts/Invoke-TrimAudit.ps1`; see `docs/TRIMMING.md` |
| `tests/ConnectOnion.Protocol.Tests/` | yes | yes | xunit unit tests for `ConnectOnion.Protocol` (wire schema, encoding, event parsing) |
| `tests/ConnectOnion.WinUIClient.UnitTests/` | yes | yes | Headless xunit tests over `Core` (projection, notifications, caches, view models), plus the ArchUnitNET layer-boundary tests |
| `tests/ConnectOnion.IntegrationTests/` | yes | yes | xunit tests against a real SQLite file (schema/migrations, repositories, identity store) |
| `tests/ConnectOnion.WinUIClient.UITests/` | yes | compile-only | FlaUI (UIA3) real-window shell smoke test. CI compiles it every run but only *executes* it on a `workflow_dispatch` opt-in, because it needs a real desktop session |

**`ConnectOnion.WinUIClient.Core` is the seam that makes the client testable, and getting a file on the right side of it is the whole game.** The app project can't be referenced by a test project — it drags in the Windows App SDK, which a headless test host can't load — so anything that needs coverage lives in `Core`, which the test projects take an ordinary `ProjectReference` on. **Moving a production file into `Core` is how you bring it under test.** If a file won't move because it pulls in XAML types, that's the signal its logic wants splitting into a WinUI-free class, not that the test project needs the Windows App SDK. Note both projects share the `ConnectOnion.WinUIClient` root namespace, so moving a file across the seam is not a namespace change. `LayoutKeys`/`KeyNames` is the worked example of the split: the key-name table is platform-free and sits in `Core`, while the layout translation P/Invokes `MapVirtualKeyW` and therefore stays in the app.

The boundary is enforced, not just described: `tests/ConnectOnion.WinUIClient.UnitTests/Architecture/LayerDependencyTests.cs` uses ArchUnitNET to fail the build if `Core` takes a `Microsoft.UI` dependency or if `Data` starts depending on `ViewModels`.

The `.sln` lives at `ConnectOnion.WinUIClient/ConnectOnion.WinUIClient.sln` even though it references every other project by relative path (`..\ConnectOnion.Protocol\...`, `..\tests\...`).

SDK pin: `global.json` sets `"version": "10.0.100"` with `rollForward: latestFeature` (any newer .NET 10 feature-band SDK works).

## Commands

Everything except `ConnectOnion.Protocol.LiveTest` is in the solution; the test projects are also runnable one at a time by `.csproj` path.

```powershell
# Restore + build the solution (app, core, protocol, conformance, all four test projects)
dotnet restore ConnectOnion.WinUIClient\ConnectOnion.WinUIClient.sln -p:Platform=x64
dotnet build ConnectOnion.WinUIClient\ConnectOnion.WinUIClient.sln --configuration Debug --no-restore -p:Platform=x64

# Run the app unpackaged (no MSIX deploy step needed)
dotnet run --project ConnectOnion.WinUIClient\ConnectOnion.WinUIClient.csproj -p:Platform=x64 -p:RunUnpackaged=true

# Protocol unit tests (xunit) — the test-writing target for wire-protocol work
dotnet test tests\ConnectOnion.Protocol.Tests\ConnectOnion.Protocol.Tests.csproj
dotnet test tests\ConnectOnion.Protocol.Tests\ConnectOnion.Protocol.Tests.csproj --filter "FullyQualifiedName~InputMessageBuilderTests"

# Headless Core unit tests (incl. the ArchUnit layer gate), and SQLite integration tests
dotnet test tests\ConnectOnion.WinUIClient.UnitTests\ConnectOnion.WinUIClient.UnitTests.csproj
dotnet test tests\ConnectOnion.IntegrationTests\ConnectOnion.IntegrationTests.csproj

# Protocol conformance gate (matches CI exactly)
dotnet run --project ConnectOnion.Protocol.Conformance\ConnectOnion.Protocol.Conformance.csproj --configuration Release

# Real-window FlaUI smoke test. Skips itself unless pointed at an executable, so build the app
# unpackaged first — the plain bin\...\win-x64\ exe from a normal build has no Windows App SDK
# bootstrapper and dies on launch.
$env:CONNECTONION_UI_TEST_EXE = (Resolve-Path 'ConnectOnion.WinUIClient\bin\x64\Debug\net10.0-windows10.0.19041.0\win-x64\ConnectOnion.WinUIClient.exe')
dotnet test tests\ConnectOnion.WinUIClient.UITests\ConnectOnion.WinUIClient.UITests.csproj

# Live protocol smoke test against a real deployed agent (not in CI)
dotnet run --project ConnectOnion.Protocol.LiveTest\ConnectOnion.Protocol.LiveTest.csproj -- <directUrl> <address> "<prompt>"

# Launch-time and memory benchmark (needs a real desktop session; not in CI). Measures the
# Release unpackaged build only — see docs/PERFORMANCE.md for budgets and the current baseline.
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\Measure-Performance.ps1

# Trimming gate evidence: both app publishes, the app-owned vs third-party warning split, and the
# trimmed smoke harness run as persist -> restart -> verify. See docs/TRIMMING.md.
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\Invoke-TrimAudit.ps1

# Just the trim-safety checks, untrimmed but with the reflection fallback already off (fast loop)
dotnet run --project tests\ConnectOnion.TrimSmoke\ConnectOnion.TrimSmoke.csproj -- all
```

`Platform` must be `x64`, `x86`, or `ARM64` for the WinUI project — `Any CPU` doesn't work for packaged debugging. Visual Studio F5 (Debug/x64, Deploy checked for `ConnectOnion.WinUIClient` in Configuration Manager) is the most reliable path for XAML debugging; `dotnet run -p:RunUnpackaged=true` is the fast CLI loop.

CI (`.github/workflows/ci.yml`, `windows-latest`) restores, audits dependencies for known vulnerabilities (`dotnet list package --vulnerable --include-transitive`), builds the `.sln` in Release/x64 with packaging disabled, runs the three headless test projects with Cobertura coverage collection, compiles the UI smoke test, publishes a ReadyToRun unpackaged build with trimming disabled, uploads coverage, and ends on the Conformance gate. Trimming is deliberately off and **`docs/TRIMMING.md` is the gate that decides when it comes back** — the reflection-based JSON that caused the original trim-only restoration failure is fixed and a trimmed smoke harness proves it, but the signed-MSIX, real-window and performance criteria are still open. `TrimmingGateTests` fails the build if the Release or CI setting changes before then. It does **not** run `ConnectOnion.Protocol.LiveTest` (needs a live agent), and it only *executes* the FlaUI smoke test on a `workflow_dispatch` with `run_ui_smoke` checked (against the published exe). The test steps deliberately omit `-p:Platform` and rebuild rather than passing `--no-build`: the solution build maps the conformance project to `Any CPU`, so forcing the platform through to a standalone `dotnet test`/`dotnet run` sends it looking for output under `bin\x64\...` that the solution never produced — hence the workflow's env var being named `BUILD_PLATFORM` rather than `PLATFORM`, which MSBuild would auto-import as `$(Platform)`. There is a comment in the env block about exactly this.

There is no lint/format command configured for this repo.

## Local data

SQLite at `%AppData%\ConnectOnion\connectonion.db` when run unpackaged (`dotnet run`), or under `%LOCALAPPDATA%\Packages\ConnectOnion.Desktop_<publisher hash>\LocalState\ConnectOnion\` when run packaged/installed/deployed from Visual Studio. WAL journal mode, foreign keys on. **That folder name is derived from the package identity (`Name` + `Publisher`), which is why neither can ever change** — a package with a different pair installs beside the old one and cannot see its data, silently. See `docs/RELEASE.md`.

`AppStorage` selects that deployment-specific root explicitly: `ApplicationData.Current.LocalFolder`
when package identity exists, `%AppData%` otherwise, and `CONNECTONION_DATA_ROOT` for isolated
automation. On the first packaged launch it moves data left by pre-release builds from virtualized
`LocalCache\Roaming\ConnectOnion` into `LocalState\ConnectOnion` before opening SQLite.

**Schema changes go through `Data/SchemaMigrator.cs` — `CREATE TABLE IF NOT EXISTS` alone cannot evolve a table that already exists.** `AppDatabase.EnsureInitializedAsync` first ensures the baseline (`CreateSchemaAsync`), then steps any older database forward. The version lives in SQLite's own `PRAGMA user_version` (a header integer: no table needed, no query cost, and written inside the same transaction as the migration it records) — not in `app_meta`. To add a column: append one `Migration(n, sql)` to `SchemaMigrator.Migrations` and bump `LatestVersion`; never edit or renumber a released migration, because databases in the wild have already recorded running it. Each migration runs in its own transaction, so schema change and version bump commit together or not at all. `user_version == 0` means "never versioned" and is stamped as the version-1 baseline (pre-versioning builds produced exactly that shape); a database at a version *newer* than this build throws rather than running against a shape it doesn't understand. Deleting the `.db` file still works to reset dev state, but it is a convenience — no longer the upgrade path.

Tables: `app_meta`, `agents`, `sessions` (incl. `mode`, schema v3 — the conversation's approval mode; see "Stop and mode" below), `preferences`, `messages` (one row per chat bubble, not a JSON blob — see the WinUI client architecture notes below), `message_attachments` (attachment **metadata only**: kind/filename/mime/size/cache-path — never the base64 payload), `executions`, `trace_events`, `identity_keys` (`private_seed` and `mnemonic` (schema v5) are DPAPI-protected (`CurrentUser` scope) blobs, base64-encoded — never plaintext), `usage_events` (schema v2).

Deleting a conversation is **not** an FK cascade — the children are deleted explicitly, in order (`ConversationRepository.DeleteConversationAsync` → attachments + messages; `DeleteExecutionsAndTracesAsync` → traces + executions), and only then does `SessionRepository.SaveAsync` remove the `sessions` row. The FKs declare no `ON DELETE`, so getting that order wrong raises a constraint violation that the repositories' `try/catch` swallows into a log line. Keep the order.

`usage_events` is the **token-usage ledger** and is the deliberate exception to all of the above: it has **no foreign key** and is **never** touched by conversation or agent deletion. Usage records that tokens were *spent*, which stays true after the chat is gone; a cascade would make the Usage panel's totals silently shrink whenever a user tidies their sidebar. `conversation_id`/`agent_id` are therefore allowed to dangle (they exist only for drill-down, which must `LEFT JOIN` and tolerate a miss), and `agent_name` is snapshotted at write time so a deleted agent's rows can still be labelled. The only code path that ever deletes from it is `UsageRepository.ClearAsync`, reached solely from the explicit, confirmed "Clear usage history" button in Settings → Usage.

**SQLite here is `winsqlite3` — the copy that ships with Windows — and it is built without local-time support.** `date(…, 'localtime')` returns **NULL**, so a query grouping on it yields no rows at all and the caller's `try/catch` turns that into a silently empty panel rather than an error. Convert to local time by arithmetic instead: `date((created_at + $offset_ms) / 1000, 'unixepoch')` with the offset passed as a parameter, which is what `UsageRepository.GetDailyTotalsAsync` (the heatmap's per-day aggregation) does. One offset covers the whole window, so a call within an hour of midnight can land in the neighbouring day across a DST boundary — accepted deliberately; carrying historical offsets would need a time-zone table SQLite does not have.

`IdentityStore` distinguishes *nothing stored* (first run → generate quietly) from *stored but unreadable* (a copied `.db`, a restored profile, or a pre-DPAPI row). The second case still regenerates — there is nothing to recover — but it is **not silent**: it raises `IdentityStore.IdentityReset`, latches `WasReset`/`ResetReason`, and `MainWindow` surfaces an error toast, because the app's address changes and every agent that authorized the old one must authorize the new one. Don't collapse those two paths back together.

**DPAPI is what keeps the database safe and also what makes it useless as a backup** — a copied `.db` or a new machine cannot decrypt the seed. So a new identity is minted from a BIP39 phrase (`AgentIdentity.GenerateWithMnemonic`) and the phrase is stored beside it, DPAPI-protected the same way; `IdentityStore.ExportBackup`/`ImportMnemonic`/`ImportSeed` and Settings → Identity are the user-facing half, and `NewlyCreatedMnemonic` is a latch (like `WasReset`) that `MainWindow.RevealNewRecoveryPhraseIfAny` shows once, because the identity is usually created before a window exists. **The derivation is a cross-client contract, not an implementation detail**: `ConnectOnion.Protocol/Bip39.cs` matches the Python SDK's `address.py` and oo-chat's `use-identity.ts` byte for byte (PBKDF2-HMAC-SHA512, 2048 rounds, salt `"mnemonic"`, first 32 bytes of the seed used directly as the Ed25519 seed — no BIP32/SLIP-0010 path), so the same phrase restores the same `0x` address in all three. `Bip39Tests` pins it against vectors generated by those references; changing any of it silently breaks every written-down phrase. Identities created before schema v5 have `mnemonic IS NULL` forever — nothing can derive a phrase for an existing seed, and regenerating one to give it a phrase would change the address every agent already authorized, so those back up via their raw seed instead. `ImportMnemonic`/`ImportSeed` raise `IdentityReplaced`; the caller must drop every live socket (they authenticated as the old address) and the restore UI refuses while a run is active.

Image cache for received `agent_image` attachments lives under the selected app-data root at `cache\images\`, filenames are the content's SHA-256 hash (never trust a remote-provided filename).

## Architecture

### Protocol layer (`ConnectOnion.Protocol`)

Deliberately has zero WinUI/platform dependency so it's unit-testable headless. This is where wire-format logic belongs — don't duplicate JSON parsing in the WinUI layer.

- **`AgentConnectionService`** — the WebSocket state machine (C# port of the TS SDK's `remote-agent.ts`): opens/authenticates via `CONNECT`→`CONNECTED`, sends `INPUT`, resolves on `OUTPUT`. Interactive turns (`ask_user`, `approval_needed`, `plan_review`) and onboarding are surfaced as dedicated C# events, not lumped into the generic stream; everything else (`thinking`, `tool_call`, `tool_result`, `llm_call`, `llm_result`, `assistant`, `agent_image`, `intent`, `eval`, `compact`, `tool_blocked`, `files_received`) is forwarded as a generic `StreamEvent` carrying the raw JSON for the ViewModel to interpret. A 60s silence watchdog is the only bounded wait — `ask_user` legitimately pends on a human indefinitely.
- **`WireMessage`** — thin `JsonElement` wrapper (`GetString`/`GetBool`/`TryGet`), not raw `JsonDocument.Parse` scattered around. Outgoing messages are plain `Dictionary<string, object?>` (no source-gen context, no attribute-based DTOs) — follow this convention for new message types rather than introducing typed request/response classes.
- **`WireJson`** — serializes those dictionaries, and **is the only way an outgoing frame reaches the socket**. Never `JsonSerializer.Serialize(dict)`: `PublishTrimmed=true` sets `JsonSerializerIsReflectionEnabledByDefault=false`, so the reflection serializer *throws* rather than merely risking a trimmed member, and this call site covers every frame the client sends. It is a hand-written `Utf8JsonWriter` (sibling of `CanonicalJson`, which does the same for signing with the relaxed encoder), byte-identical to the reflection serializer's output — insertion order, default escaping, no indentation — and its `WriteValue` throws on an unrecognised value type rather than guessing, so a builder putting something new on the wire fails in `WireJsonTests`. **Two sanctioned JSON mechanisms exist and there is no third:** a source-generated context (`AppJsonContext`, `ConversationJsonContext`) for blobs we define and read back out of our own database, and `WireJson`/a hand-written `Utf8JsonWriter` for shapes the host defines. See `docs/TRIMMING.md`.
- **`InputMessageBuilder`** — pure function building the `INPUT` frame dict; kept separate from `AgentConnectionService` specifically so the exact wire shape (text-only / images / files / mixed) is unit-testable without a live socket.
- **`AttachmentModels`** — `DataUrlCodec` (encode/decode `data:` URLs, and the size-limit math replicated from the Python host's `validate_files`: the server measures the **encoded string length**, not raw bytes, so client-side preflight must too) and `AttachmentWireEvents` (typed parsers for the real `agent_image`/`files_received` wire events — see "Multimodal attachments" below for the full protocol contract).
- **`EndpointResolver`** — relay lookup, cached `/health` reachability probing, and separately cached `/info` fetch/parsing (`AgentAcceptedInputs`/`AgentFileInputs` capability model).
- **`AgentIdentity` / `CanonicalJson` / `Hex`** — Ed25519 identity and canonical-JSON signing, verified byte-for-byte against `ref-sign.js` by the Conformance project.

### Core layer (`ConnectOnion.WinUIClient.Core`)

The client's logic, minus everything that needs a window. It references `ConnectOnion.Protocol` and takes only headless packages (`CommunityToolkit.Mvvm`, `Microsoft.Data.Sqlite.Core`, `Microsoft.Extensions.Logging.Abstractions`, `System.Security.Cryptography.ProtectedData`); the app project references *it*. Everything the "Local data" section above describes (`Data/`: `AppDatabase`, `SchemaMigrator`, the repositories, `IdentityStore`) lives here, along with `Models/`, `Services/Notifications/`, `Services/Runtime/` (`ChatTurnProjection`, `AgentConnectionRegistry`, the projectors), `Services/Attachments/` (validation + encoding), `ConversationCache`, and the WinUI-free view models.

It still targets `net10.0-windows10.0.19041.0` rather than plain `net10.0` — it needs Windows-only APIs like DPAPI — but that is *not* a licence to reach for `Microsoft.UI`; the ArchUnit test named above is what stops it. Anything that must touch a `Window`, a `DispatcherQueue`, a picker, or a XAML type belongs in the app project instead.

### WinUI client (`ConnectOnion.WinUIClient`)

**Folder layout.** The project root holds only `App`, `Program`, and the `MainWindow.xaml`/`.xaml.cs` pair; every other `MainWindow` partial lives in `Shell/` (see `Shell/README.md`). `Controls/` is grouped by surface — `Chat/`, `Agents/`, `Settings/`, `Shell/`, `Primitives/` (see `Controls/README.md`). **Both folders deliberately keep the namespace they had before the grouping** (`ConnectOnion.WinUIClient` and `ConnectOnion.WinUIClient.Controls` respectively), so folder ≠ namespace here and that is intentional, not drift: a partial class can only have one namespace, and a control's namespace is what 24 XAML files name in their `xmlns` and what each `x:Class` must match. Nothing enforces folder/namespace agreement in this repo (`Directory.Build.props` sets `EnforceCodeStyleInBuild` but IDE0130 is not on), so grouping stays free. `Primitives/` carries one rule: no view-model or feature-model references.

`Program` combines Windows AppLifecycle redirection with a named mutex derived from
`AppStorage.RootDir`. AppLifecycle handles ordinary second activation of the same installed or
unpackaged executable; the data-root mutex also prevents two portable versions extracted to
different folders from opening the same SQLite and identity store. Isolated automation roots get
different mutex names and can still run side by side.

MVVM via **CommunityToolkit.Mvvm** (8.4.2) source generators — models/view models are `partial` classes deriving from `Common/ObservableObject.cs`, a thin bridge over `CommunityToolkit.Mvvm.ComponentModel.ObservableObject` (kept as a named base so the many `: ObservableObject` declarations need no churn, and so the generators run on subclasses). `[ObservableProperty]` is applied to **partial properties** (`public partial T Foo { get; set; }`), not backing fields — this is the WinUI/CsWinRT-recommended form and keeps the build free of the `MVVMTK0045` AOT advisory (no suppression). Because a partial-property declaration can't carry an initializer, **non-null defaults are seeded in the constructor**; a `{ get; private set; }` accessor list preserves read-only-to-XAML encapsulation. Use `[NotifyPropertyChangedFor]` for derived properties, `partial void On<Prop>Changed` hooks for setter side-effects, and `[RelayCommand]`/`[NotifyCanExecuteChangedFor]` for commands. Attributes that must land on the property (JSON, etc.) go **directly on the partial property** (no `[property: …]` target). Keep a property hand-written (still calling the inherited `SetProperty`) only when its setter must *transform* the incoming value — `SessionSummary.Mode` normalizes to a valid mode, and `SessionsViewModel.Selected` skips persistence on the load-time assignment — which `[ObservableProperty]` deliberately can't express. **Dependency injection** is the .NET **Generic Host** (`Microsoft.Extensions.Hosting`): `App` builds an `IHost` in its constructor, all singletons + view models are registered in `Services/ServiceRegistration.AddAppServices`, and `App.Services` is the composition root. **View models take their dependencies as constructor parameters** and are registered `Transient` — a page obtains its one via `App.GetService<XyzViewModel>()` in its ctor, because WinUI instantiates pages/controls/windows itself (parameterless ctor, `Frame.Navigate`), never through the container. `Services/AppServices.cs` is a typed accessor over `App.Services` (get-only static properties) that framework-created **code-behind** uses to reach shared singletons — the DI boundary WinUI's view model imposes, not a service-locator by choice. Startup wiring runs as an `IHostedService` (`NotificationStartupService`, started in `OnLaunched` after the storage dirs exist). `ILogger<T>` is available to any injected type. Register a value-transforming or two-same-type-parameter service with a factory lambda (see `NotificationCoordinator`); everything else is auto-wired.

The shared `HttpClient` is **resilient via Polly** (`Microsoft.Extensions.Http.Resilience`): `ServiceRegistration` registers a named client (`"agent"`) with an `AddResilienceHandler` pipeline — `AddRetry` (2 attempts, jittered exponential backoff) then `AddTimeout` (10s per attempt) — and the singleton `HttpClient` is that named client from `IHttpClientFactory`. Every agent HTTP call inherits it with no call-site code: `/health` presence probes, detail-page `/info` fetches, the relay lookup `EndpointResolver` makes with the passed client, and agent-image downloads all flow through this one client. **No circuit breaker on purpose** — a presence probe must keep retrying a flaky agent, not latch it "offline" until a breaker half-opens — and callers already impose their own overall timeouts, so the pipeline only adds retries within that budget. `ConnectOnion.Protocol` stays Polly-free: it receives the already-resilient `HttpClient` as a parameter.

- **Pages own their ViewModel** as a `public XyzViewModel Vm { get; } = App.GetService<XyzViewModel>();` property (resolved from the container — see the DI note above); XAML uses `x:Bind` against `Vm.*`, code-behind wires routed events (`Click`, `PointerEntered`, etc.) that call `Vm` methods. **Large types are split into partial-class files named `Type.Aspect.cs`, and that is the repo's standard answer to a file growing past ~500 lines** — not a new class, not regions. `ChatViewModel` is `ChatViewModel.cs` (state, properties, conversation load/restore, `IChatProjectionTarget`), `.Run.cs` (send/stop/mode and folding run snapshots into the list), `.Conversation.cs` (new/branch/retry — the operations that re-point the run subscription), and `.StreamEvents.cs` (stream-event → `ChatMessage` mapping, interactive-turn bubbles, per-turn token/duration aggregation). `ChatPage` is `ChatPage.xaml.cs` (lifecycle, navigation, load) plus `.Scrolling.cs` (scroll/stick-to-bottom/load overlay — the timing-sensitive part), `.MessageActions.cs`, `.Attachments.cs`, `.Interactive.cs`, and `.Find.cs`. The same idiom carries `ConversationRepository.Mapping.cs` (row↔object SQL plumbing, split from the public repository API) and `ChatTurnProjection.Events.cs` (the per-event-type dispatch table — **this is the file to edit when the agent gains a new event type**).
- **The run runtime owns connections and turns, not pages** (`Services/Runtime/`): `AgentSessionManager` (app-level, on `AppServices`) holds the per-conversation WebSockets (`AgentConnectionRegistry`) and drives each turn through the headless `ConversationRunRegistry`. It persists the user message on send, buffers the run's stream events, and — when the reply lands — projects them into bubbles and writes them *before* publishing the run's terminal state, so a page opened mid-turn loads history from SQLite and replays the live events on top instead of double-rendering them. A `ChatPage` only ever `Subscribe`s; closing it does not cancel the turn, and a turn completes (and notifies) with no page open at all. `ChatTurnProjection` is the single stream-event → `ChatMessage` mapping, driven identically by the live view model (`IChatProjectionTarget` over the `ObservableCollection`) and by the headless persist path (over a plain list) — put new event handling there, never in one of the two callers.
- **Chat list rendering and caches**: `ChatPage.xaml` has one `DataTemplate` per bubble kind dispatched by `Common/ChatMessageTemplateSelector` — don't collapse them back into a single template that builds every bubble variant and hides all but one with `Visibility`, which is what made scrolling expensive. `Services/ConversationCache` keeps the last 4 *idle* conversations in memory (real LRU; invalidated when a session/agent is deleted, and never used for a conversation with an active run — that must load the authoritative persisted history). Cached messages must never retain live `ApprovalResponder` delegates: those instance-method callbacks point back to the page's transient `ChatViewModel`, so cleanup clears them before releasing the message list. `Common/LocalPathToImageSourceConverter` decodes attachment thumbnails at the 280px the templates render at and keeps only weak `BitmapImage` references by path, because virtualization re-runs the converter for the same paths but the cache must not own decoded native surfaces after a page exits.
- **Live turn usage**: `ChatTurnProjection` already accumulated the turn's tokens/context/tool-calls for its closing summary row; `CurrentUsage` publishes that running total mid-turn through `IChatProjectionTarget.ReportUsage`, and `ChatViewModel.LiveUsageText` renders it beside the composer's connection status. Published from the `llm_result` arm only — it is the one arm that moves those numbers, and announcing after every event would push an unchanged value dozens of times a turn. It is the **running total**, not a per-iteration figure (which would flicker and answer a question nobody asks), it **resets per turn** via `OnIsProcessingChanged` (carrying the last turn's total forward would read as the new turn having spent it before it began), and an agent reporting nothing yields `TurnUsage.IsEmpty` → empty string → the slot collapses, because unreported is not the same as zero. The headless persist target ignores the report; the same figures still reach storage through the summary row.
- **Tool timeline rendering** (`Controls/Chat/ToolActivityView.xaml` over `Models/ToolActivity.cs`): one card per turn, one row per tool. A row shows the tool's name, **what it was given**, and what came back. That middle part is `Models/ToolInvocation.cs` — `ToolInvocations.Read(toolName, argumentsJson)` classifies a step into a family (Command / Search / Path / Url / Task / Text) and pulls the shell command, pattern, URL or delegated task out of the arguments, with a two-pass name lookup (exact table, then ordered keyword scan) for exactly the reason `ToolIcons` has one — `remote_bash` and `fs.writeFile` have to reach the same family as `bash` and `write`. **Add a tool family there, not in the view.** Two decisions worth keeping: it is derived at *render* time from the already-persisted `Arguments` (like `IconKind` is from `ToolName`), so it costs no column and conversations recorded before it existed show their commands as soon as they are reopened; and the row's target digest (`ShowDisplayTarget`) and the inline one-liner (`ShowInlineInvocation`) both stand down when the fuller form is on screen, so a grep row never reads "Search: TODO" above a line saying "TODO". A step renders its output as either a monospace log or markdown prose, decided by `ToolInvocations.ProducesMarkdown` — an explicit opt-in list (`load_guide` and friends), **never a guess from the content**, because a shell transcript or a stack trace depends on its exact whitespace and a `#` in program output is not a heading; a failed step always takes the log branch for the same reason. Note the `$` prefix carries **no trailing space** — XAML collapses whitespace between adjacent inlines, so the gap is a panel `Spacing` in the row and `ToolInvocation.DisplayText` in the wrapping block.
- **Process-wide memory bounds**: `AgentConnectionService` caps an incoming WebSocket text frame at 80 MiB (enough for the 50 MiB image limit after base64 expansion) and closes oversized frames with `MessageTooBig`; `EndpointResolver` prunes expired entries and caps each endpoint/info cache at 128 keys; `ConversationRunRegistry` retains at most 64 terminal snapshots and never retains their raw events; the highlighted-text font metric cache is capped at 32 combinations. Deleting a conversation/agent must also clear its socket-wiring, run snapshot, config, presence, and notification state. Keep `ConversationCache` as the four-entry LRU: a byte-weight experiment made large conversations rebuild on every navigation and increased transient/native pressure. Because small managed wrappers own much larger native XAML document trees, every fourth fully detached `ChatPage` serially schedules a background Gen2 collection without waiting for apartment-sensitive finalizers or compacting the LOH. The real-window memory gate defaults to 24 measured cycles, 6 warm-ups, and 750 ms settling, with each scenario in a fresh process.
- **Chat message persistence**: `messages` is one row per rendered bubble (not a serialized envelope), keyed `(conversation_id, id)`. Writes are **incremental** — `ConversationRepository.UpsertMessagesAsync` is the only write path and touches only the rows handed to it (`INSERT ... ON CONFLICT(conversation_id, id) DO UPDATE`, `created_at` left alone on update); each written row's attachments are replaced wholesale by a `message_id`-scoped delete plus re-insert, because an attachment's id is content-derived and an existing agent bubble can gain an image mid-turn. Nothing reads or rewrites the whole conversation on a save, so a turn costs O(turn), not O(conversation). The persist path (`AgentSessionManager.LoadTurnWindowAsync`) therefore loads only what a turn's projection can actually touch: `GetNextMessageIdAsync` (a `SELECT MAX(id)+1`, no rows) plus `LoadLastAgentMessageAsync` — that one row is the seed because an `agent_image` event hangs its attachment on the last agent bubble and the final reply is deduped against it. If you add a projection step that mutates an *older* row, that window is what you have to widen. `ChatMessage` carries generic `Event*` fields (`EventKind`, `EventTitle`, `EventDetail`, `EventArgs`, `EventMeta`, `Status`) reused across very different bubble types (`activity`, `tool_activity`, `ask_user`, `approval`, `plan_review`) — check `EventKind` before assuming what a field means for a given bubble.
- **Stop and mode** (`AgentModes`/`ApprovalRejectModes` in the protocol library; `AgentSessionManager.RequestStopAsync`/`SetModeAsync`). Two facts about the host drive this whole design, and both are counter-intuitive enough to be worth stating before you touch it:
  - **Global Stop is `{"type":"INTERRUPT"}`.** It is fire-and-forget on the active socket: the current tool is allowed to finish and the host stops at the next iteration boundary, so the UI stays in `STOPPING`, blocks new `INPUT`, and waits for `OUTPUT`/`ERROR`. Duplicate INTERRUPT frames are valid and are sent rather than client-deduplicated. An approval card has a separate immediate Stop action: it answers that approval with `{approved:false, mode:"reject_hard", feedback?:...}`, locally settles the run, and restores input without waiting for OUTPUT. Skip and Explain use `reject_soft` and `reject_explain` respectively; never substitute one scope for another based on `_pendingInteractive`.
  - **A `mode_change` frame only reaches the agent while a turn is running** (the host's ws_router forwards non-CONNECT/INPUT frames only when an `active_io` exists) and it is applied at the next iteration boundary. A mode in CONNECT's `session` only survives for a session the host has never run, because `merge_sessions` replaces our session wholesale whenever the server's iteration count is higher — which it always is, since we report none. So **the mode is client-owned state** (`sessions.mode`), and `SendInputAsync` re-asserts it by sending `mode_change` *immediately after* the INPUT, on the same socket, every turn. Reverse direction matters too: the agent can call `enter_plan_mode()` itself, so `mode_changed` is both a typed event and a stream event, and the view model follows it rather than re-asserting the user's last pick. ULW is deliberately unsupported — its checkpoint blocks the agent on `io.receive()` and would hang the turn without a `ULW_RESPONSE` card.
- **Onboarding gates** (`ONBOARD_REQUIRED` → `AgentInteractiveParsers.ParseOnboard` → `OnboardRequest`): the agent's trust gate names what it accepts in `methods` — `invite_code`, `payment`, or both — plus `payment_amount` and sometimes `payment_address`. The card offers only what is on offer, and two rules keep it answerable: **no methods named means offer the invite code** (that is the near-universal gate, and showing nothing would strand the user on a card with no way through), and **a payment gate with no quoted amount is not offered** because there is nothing to act on. `payment_address` is read, never derived — the agent's own address is not a safe stand-in, and an invented destination for a real transfer loses the user's money, so an absent address renders no address block. The payment button is the user *asserting* a transfer already happened (`ONBOARD_SUBMIT` with `payment`); nothing in the client moves money and the agent verifies the claim itself. Unlike `InviteCode`, a payment claim is deliberately **not** stored for auto-resubmission on reconnect — re-asserting it would report a second payment that never happened.
- **Credentials in interactive turns**: an `ask_user` carrying `fields` is a login form, and the password it collects reaches the local database through **two** doors. The wire answer (`InteractiveResponseBuilder.BuildAskUserAnswer`) must stay complete — the agent asked for it because it needs it — but the *summary* is what lands on the resolved card and in the persisted `event_meta` column, so it goes through `BuildAskUserAnswerSummary`, which masks any field whose `type` is `password` **or** whose name looks like a secret (an agent is not obliged to set the type). The second door is the agent typing that password into a browser: those tool arguments are persisted too, and nothing in `{"text":"hunter2"}` names it a secret. `SessionSecrets` (process-wide, in-memory, never persisted) remembers what the user submitted and `ToolActivityProjector.SanitizeText` masks **exact** matches only — a substring rule would turn a short password into a censor that fires on ordinary words. Also note `SanitizeJson` serializes with `UnsafeRelaxedJsonEscaping`: the default encoder escapes `+`, `&`, `<`, `>` and all non-ASCII, which rendered every search URL as `Sydney+weather` and every Chinese argument as `\uXXXX`. That encoder name warns about HTML/JS injection contexts, which this path (XAML `TextBlock`, parameterized SQLite, re-parsed JSON) is not — don't copy it somewhere that is.
- **Interactive turns** (`ask_user`/`approval_needed`/`plan_review`) render as persistent inline chat bubbles with live controls (submit button, approve/reject, etc.), not `ContentDialog` popups — this matches the reference web client's chat-item-feed model and keeps the decision visible in history. Their live *control* state (options/fields/free text) is intentionally **not** persisted to SQLite — once the WebSocket session is gone, answering is meaningless. The *resolved result* is persisted, though: the reply-less event stream can't carry the user's answer, so when the page answers it calls `AgentSessionManager.RecordInteractiveAnswer`, and at turn-persist time `ResolveInteractiveCards` stamps the chosen result onto the re-projected card's `EventMeta`/`Status`. Any interactive card a persisted (terminal) run left unanswered is sealed as `"No selection"` — so reloaded history shows what was chosen (or that nothing was) instead of dead, unanswerable controls.
- **Multimodal attachments**: outgoing images/files are picked via `AttachmentPickerService` (`FileOpenPicker`, HWND resolved through the static `App.MainWindow` since `ChatComposer` is a `UserControl` with no HWND of its own), preflight-validated via `AttachmentValidationService` against the agent's real `/info` capability (client-side checks are a UX nicety — the server remains the final authority), and encoded off the UI thread via `AttachmentEncoder` right after validation passes (never re-encoded, never read into memory before validation). Incoming `agent_image` events are decoded/downloaded and cached to disk via `AttachmentImageCacheService` *before* ever touching `ChatMessage` or SQLite — the message list and DB only ever hold a local cache path plus metadata, never a base64 payload. Wire contract specifics (exactly what `images`/`files` look like on `INPUT`, what `agent_image`/`files_received` look like coming back, and what is/isn't actually enforced server-side) live in the `ConnectOnion.Protocol` doc comments above, not duplicated here — read `AttachmentModels.cs` and `InputMessageBuilder.cs` before changing this path.
- **Agent skills** (`Services/AgentSkills.cs` in `Core`, over `EndpointResolver.ParseSkillsFromInfoJson`): an agent's `/info` declares `skills`, and two surfaces consume them. The composer opens a **slash palette** while the draft is a `/`-command still being typed — `AgentSkills.TryGetSlashQuery` says when that is, and **the space is the commit**: past it the palette closes and Enter goes back to sending, which is what stops a completed command's arguments from being swallowed. Matching is deliberately forgiving and ranked prefix → substring → in-order letters, so `/linkedeng` finds `linkedin-engagement`; `OrderBy` is stable so equal-ranked skills keep the agent's declared order and the highlighted row does not move under the user's arrow keys between keystrokes. The agent-detail page turns the best few skills into **opening chips** (`AgentSkills.BestOffers`) — internal/debug skills are dropped from the chip row only (they stay in the palette, where typing the name means it), descriptions that will not cut into a clean short offer yield null rather than a truncated one, and an agent with no usable descriptions falls back to the composer's three generic starters. `ShowSuggestions` is on for `AgentDetailPage` and off for `ChatPage`: chips answer "what do I even ask this thing", which is only a question before the conversation starts. Both view models read skills from the same cached `/info` as `AcceptedInputs`, so neither costs an extra round trip.
- **Drag-and-drop attachments**: `Controls/Chat/ChatComposer` is the only real drop target — `AttachmentDropService` (the drop counterpart to `AttachmentPickerService`) classifies dropped `StorageFile`s by extension (no file-type filter like the picker gets) into `PendingAttachment` drafts, which still flow through the same `AttachmentValidationService`/`AttachmentEncoder` pipeline; dropped folders are skipped silently rather than recursively expanded. `Shell/MainWindow.DragDrop.cs` only paints a window-wide "drop it on the composer" hint (`RootGrid.AllowDrop` + handlers registered with `handledEventsToo: true` so the hint still updates after the composer's own drag handlers mark the event `Handled`) — it is not itself a drop target.
- **Global find overlay** (Ctrl+F, `Shell/MainWindow.ViewMenu.cs`): pages that support in-content search implement `Views.IFindHost` (`OpenFind`/`CloseFind`/`SetFindQuery`/`SelectNextFindMatch`/`SelectPreviousFindMatch`, plus a `FindStateChanged` event); `MainWindow` attaches to whatever `ContentFrame.Content` currently is and drives one shared find UI (`FindOverlayPanel`/`FindTextBox`) against it — add `IFindHost` to a new page rather than building a page-local find UI.
- **Keyboard shortcuts are data, not literals.** `Services/KeyboardShortcutCatalog` (in `Core`) is the single source of truth for every shortcut the app advertises; adding a customizable entry there is what makes it real, and there is no second place to edit. Entries split two ways: the **customizable** 14 are the ones the app dispatches itself (`Shell/MainWindow.FileMenu.cs`/`ViewMenu.cs`/`HelpMenu.cs`), and the **non-customizable** rest are listed only so the shortcuts dialog stays complete — the app doesn't own their key (a `TextBox` handles Ctrl+C natively; the composer's Enter is the Enter-key preference; Esc belongs to whatever has focus) and each carries a reason string saying so. `KeyboardShortcutService` (singleton) resolves catalog default + user override into the live chord and answers the handlers' `IsShortcut(id, keyCode, ctrl, shift, alt)` question, so **handlers never compare key codes themselves**. Overrides persist as canonical strings (`"Ctrl+Shift+N"`) in `preferences.shortcut_overrides_json` — a pre-existing baseline column shared with the unrelated `composer.enterKey` entry, which the service is careful to leave alone. Several deliberate behaviors worth not "fixing": a rebind onto a chord another action holds is **refused**, not stolen (a silently-dead shortcut is unnoticeable); rebinding back to the factory chord **deletes** the override row rather than pinning it, so a future default change still reaches that user; an override that no longer parses falls back to its default rather than leaving the action unfireable; and `Rebuild` seeds defaults first and resolves collisions by catalog order, so a colliding stored pair loses deterministically instead of by dictionary iteration order. `KeyChord` holds a **raw Win32 virtual-key code**, not `VirtualKey`, purely so it stays WinRT-free and headlessly testable. `Shell/MainWindow.Shortcuts.cs` pushes live chords into `KeyboardAcceleratorTextOverride` on the 14 menu items (subscribing to `BindingsChanged`, hopping to the UI thread — the service saves on a background task), because a XAML literal would advertise a combination that no longer fires. `KeyboardShortcutStartupService` (`IHostedService`) loads the overrides at host start; until it completes the service answers with catalog defaults, so a keystroke during startup still works.
- **Sidebar** (`Controls/Shell/ShellSidebar.xaml[.cs]`): `ItemsRepeater`-based agent/session tree. Row hover and selection are unified through one `RowStateToBackgroundConverter`-driven Border per row (bound to a computed `ShowRowBackground = IsSelected || IsHovered`) rather than each sub-button showing its own independent hover — sub-button chrome is neutralized via a `Resources` dictionary declared **inline on each row's container element**, not shared through a `StaticResource` (WinUI requires a `ResourceDictionary` assigned to `FrameworkElement.Resources` to be uniquely owned per element; a shared instance throws `XamlParseException` the moment a second row tries to reuse it).
- **Color system** (`Styles/Colors.xaml` + `Styles/Brushes.xaml`, merged into `App.xaml` after `XamlControlsResources`): the single source of truth for every color in the app — a Deep Purple brand palette expanded into semantic Light/Dark tokens (`BrandPrimaryBrush`, `SurfaceElevatedBrush`, `TextSecondaryBrush`, `SidebarItemSelectedBrush`, `SearchMatchBackgroundBrush`, `UserMessageBackgroundBrush`, ...). `Colors.xaml` holds raw `Color` resources per theme; `Brushes.xaml` wraps them as `SolidColorBrush`es pages actually bind to via `{ThemeResource ...}`, **and** re-points WinUI's own themed keys (`TextFillColorSecondaryBrush`, `CardBackgroundFillColorDefaultBrush`, `AccentFillColorDefaultBrush`, `ButtonBackgroundPointerOver`/`Pressed`, `FocusVisualPrimaryBrush`, ...) at the same tokens so native Fluent chrome (Expander, default Button hover, hyperlinks) stays visually consistent without replacing any `ControlTemplate` — `ToggleSwitch`/`CheckBox`/`RadioButton` are deliberately left alone. Code-behind that needs a raw `Windows.UI.Color` (`AppWindowTitleBar` in `MainWindow.xaml.cs`) goes through `ThemeService.GetColor(key, isDark)` rather than duplicating hex literals; the composer's waveform deliberately uses ordinary XAML shapes and brushes, not a Win2D `CanvasAnimatedControl`, because constructing one per chat page creates a native swap chain and render-thread pool before recording even starts. Anything reading a `Brush` by string key (converters, `HighlightedTextBlock`, `WinUiMarkdownRenderer`) reads fresh from `Application.Current.Resources[key]` each time rather than caching, so a live theme flip never leaves stale colors on screen. A handful of pre-existing resource keys (`ShellBackgroundBrush`, `ComposerBackgroundBrush`, `StatusSuccessTextBrush`, ...) are kept as redirects onto the new tokens for source compatibility — prefer the new semantic names in new code.
- **CommunityToolkit.WinUI (UI)**: two toolkit packages back UI presentation. `CommunityToolkit.WinUI.Animations` drives entrance/exit motion on discrete surfaces — the in-app toast cards (`InAppNotificationHost` sets `Implicit.SetShowAnimations` for entry and plays an `AnimationBuilder` fade/slide on `Remove` before dropping the card, guarded by a `_dismissing` set so the auto-dismiss timer can't race the close button) and the `OfflineNoticeBar` (`Implicit.ShowAnimations` declared inline in `ChatPage.xaml`/`AgentDetailPage.xaml`). Keep animation to self-contained, non-virtualized elements — don't attach implicit animations to `ItemsRepeater`/`ListView` item roots, which fights recycling. `CommunityToolkit.WinUI.Controls.SettingsControls` provides `SettingsCard`: `SettingsPage.xaml` is the flattened Windows 11 pattern — a section-header `TextBlock` over stacked `SettingsCard`s (`Header`/`Description` + the control as content), not the old hand-rolled `SettingRow` inside a section card (removed). The cards inherit the app palette because `Brushes.xaml` already re-points the Fluent `CardBackgroundFillColorDefaultBrush`/`…Border…` keys the toolkit's default style reads.

- **Logging** is **Serilog**, configured in the `App` constructor and bridged into DI (`AddSerilog`), so injected types keep using plain `ILogger<T>`. It writes rolling daily files to `%AppData%\ConnectOnion\logs` (10 MB cap, 14 retained). The `Microsoft`, `System.Net.Http`, and `Polly` categories are pinned to `Warning` on purpose: `HttpClient` logs four lines per request and the resilience pipeline one per attempt, so every presence-probe sweep wrote ~30 lines of framework chatter and buried the app's own events. At `Warning` the interesting half — a retry that actually fired — still lands. Shutdown is `App.ShutdownAsync` (idempotent via `Interlocked`, called from `MainWindow.Closed`): it drains the run manager and stops the Generic Host under bounded timeouts, logging each phase's duration, then flushes Serilog last.
- **Localization** is scaffolded, not finished. WinUI `.resw` resources live in `Strings/en-US/Resources.resw` and views reference them by `x:Uid`; settings, shell menus, search/drop hints, chat approvals, composer suggestions/modes, offline state, and primary entry/empty states are migrated, the rest aren't. **Keep the fallback text in the XAML when you add a `x:Uid`** — it's what keeps a development build diagnosable when a resource is missing. There is no second locale yet, so nothing currently proves the indirection works.

### WinUI/XAML gotchas already paid for in this codebase

Worth knowing before you re-discover them via a build or runtime failure:

- A type referenced from an `x:Bind` `DataTemplate` needs plain `{ get; set; }` properties — `required` or `init` accessors break the compiler-generated `XamlTypeInfo.g.cs` reflection metadata with a confusing `CS9035`/`CS8852`.
- `FluentIcons.WinUI`'s `IconSize` enum only has specific values (`Size10/12/16/20/24/28/32/48`, no `Size14` etc.) — check the actual enum rather than guessing a round number.
- **`IconSize` picks a *font file*, and the small ones are not complete.** Each size is a separate `FluentSystemIcons-Size<N>.otf`, and `Size12` ships **439** glyphs against `Size16`'s 4372 — so `IconSize="Size12"` on an icon with no 12px glyph renders as `.notdef` (a blank or a box), silently, with no build error. `Copy`, `Live`, `Settings`, `Stop`, `Send`, `Image`, `Document`, `MoreHorizontal`, `Mic`, `Folder`, `Key`, and `Wrench` are all missing at 12; `Dismiss`, `ChevronUp`/`Down`, `Chat`, `Pin`, `Add`, `ArrowClockwise`, `Edit`, `Clock`, `Checkmark`, `Warning`, `Info`, `Search`, `Attach`, `Delete`, `Person`, `Bot` are present. The fix is the repo's existing idiom: request `Size16` and shrink it with `RenderTransformOrigin="0.5,0.5"` + `<ScaleTransform ScaleX="0.75" ScaleY="0.75"/>` (12/16) — see `ChatPage.xaml`'s copy buttons and the `Stop` icon beside them. Note a `RenderTransform` doesn't shrink the *layout* slot, so the icon still measures 16px; that's fine inside the 24px action buttons but check the spacing anywhere tighter. **Apply the treatment to every icon in a row, not just the missing one** — the Size12 designs carry visibly heavier strokes than a scaled-down Size16, so a row mixing the two looks wrong in both weight and spacing (this is what the chat message action rows had to be fixed for). To confirm coverage for a new icon, dump the font's glyph order rather than guessing:
  ```bash
  python -c "from fontTools.ttLib import TTFont; print('copy.regular' in TTFont(r'%USERPROFILE%\.nuget\packages\fluenticons.winui\2.2.333\contentTransitive\FluentIcons.WinUI\Assets\FluentSystemIcons-Size12.otf').getGlyphOrder())"
  ```
  (glyph names are the icon's PascalCase name in `snake_case` plus `.regular`/`.filled`).
- `Microsoft.UI.Xaml.EventTrigger` has no `RoutedEvent` property (that's WPF-only); it always fires on `Loaded` implicitly. A XAML-declared `Loaded`-triggered `Storyboard` needs `<EventTrigger>` with no `RoutedEvent` attribute, or just start the `Storyboard` from a code-behind `Loaded` handler — the latter is what this repo uses for the sidebar's online-status breathing animation.
- `Style` setters can't target `Resources` (not a `DependencyProperty`); scope resource overrides by declaring them inline on the actual element instance instead.
- **`x:Load="False"` does not work for `MainWindow.xaml`'s children, and fails silently.** Deferring the three modal overlays was tried (they are invisible at launch and `SettingsOverlay` drags in the whole `SettingsPage`): `FindName(name)` returns **null** from both `RootGrid` and the element's direct parent panel, so the `x:Name`-generated field stays null, the realization helper NREs, and the button that should open the dialog just does nothing. `MainWindow` is a `Window`, not a `FrameworkElement`, so it has no `FindName` of its own and the content root's namescope does not resolve the deferred elements. Measured payoff before it was reverted was ~9 MB of working set and **zero** launch-time change — see `docs/PERFORMANCE.md`. Don't re-attempt without a working realization path.
- **A `UserControl` with `AutomationProperties.AutomationId` in XAML is not necessarily findable by that id.** `SettingsOverlay`/`AboutOverlay`/`KeyboardShortcutsDialog` each carry one, but the control produces no automation peer of its own, so UIA never exposes the id and `ByAutomationId` returns null. UI tests must assert on a child that *is* exposed — `ShellSmokeTests` targets `GeneralNav` inside the settings overlay. Also expect a transient `COMException` (`E_UNEXPECTED`, "Catastrophic failure") from `FindFirst` while the visual tree is mutating; it means "ask again", so poll rather than fail.
- **The dispatcher keeps pumping after `Window.Closed`.** Anything still armed when the window closes — a `DispatcherTimer` tick, an `async void` continuation resuming after an awaited animation — can therefore run against a visual tree the framework is already tearing down. That surfaces as an access violation (`0xC0000005`) **inside `Microsoft.UI.Xaml.dll`**, which is native: no managed `catch` sees it, the log shows a clean shutdown a few hundred ms earlier, and under Visual Studio the debugger has usually detached by then, so Windows invokes the JIT debugger ("choose a Visual Studio version") instead of breaking. If you ever see that dialog on exit, check the Windows Application event log for the faulting module before assuming it's your code. It's a race — it reproduces intermittently and only when something was genuinely in flight.
  - `MainWindow.DetachWindowServices()` (called from `Closed`, idempotent via `Interlocked`) is where the window's own actives get disarmed **synchronously**: it stops the zoom popup's idle timer (`DetachViewMenu`) and calls `InAppNotificationHost.Shutdown()`, which stops every toast card's auto-dismiss timer and clears the stack without animating. A new window-owned timer or animation belongs in that method too. It also asks the current page to disarm itself via `Views.IShutdownDisarmable` — pages stop their timers in `Unloaded`, which is **not** guaranteed to fire on window close, so a page owning a timer (as `ChatPage` does: find debounce, thinking ticker, `ChatComposer.Dispose()`) must implement that interface rather than rely on `Unloaded`. Note the real exit funnel is `MainWindow.ExitApplication` — clicking the title-bar X only shows the "Minimize to tray / Exit" dialog, and minimizing never closes the window at all, so teardown races only exist on the Exit branch.
  - An `async void` handler that touches the tree after an `await` needs an explicit "did we shut down?" check on the far side of it — see `InAppNotificationHost.Remove`, where the exit animation's continuation would otherwise re-enter a cleared stack.
  - Page- and control-owned timers (`ChatPage._findDebounceTimer`, `ChatComposer._recordingElapsedTimer`) stop in their own `Unloaded` handlers, which covers navigation. But `Unloaded` is **not** guaranteed to fire on window close, so don't rely on it as the only disarm path for anything that would be expensive to get wrong.
