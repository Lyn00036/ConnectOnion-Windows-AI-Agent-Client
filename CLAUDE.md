
# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

ConnectOnion Desktop is a native Windows client (WinUI 3, C#, .NET 10) for chatting with ConnectOnion-compatible agents over WebSocket. The repo is C#-only: the legacy Electron + React `frontend/` and the vendored Python `agent/` examples were both deleted in `197a88d`, so any doc still pointing at them is stale — read them out of git history if you need the prior UX behavior, and don't reintroduce those trees.

Prose docs live in `docs/` (see `docs/README.md`): the wire protocol (`SESSION_MESSAGE_STRUCTURE.md`), the test plan and backlog (`TEST_PLAN.md`), the requirements brief, engineering optimization notes (`OPTIMIZATION.md`), and a historical record of the Electron → WinUI migration. **This file is the authoritative description of the architecture — where a document in `docs/` disagrees with it, this one is right.**

## Solution Layout

Production projects sit at the repo root; every test project lives under `tests/`. All but one are wired into the `.sln` — keep this in mind when running `dotnet build`/`dotnet test` against the solution vs. a project directly:

| Project | In `.sln`? | In CI? | Purpose |
|---|---|---|---|
| `ConnectOnion.WinUIClient/` | yes | build | The WinUI 3 app: XAML, code-behind, and the services that need a window or the Windows App SDK (`net10.0-windows10.0.19041.0`) |
| `ConnectOnion.PortableLauncher/` | yes | build + release | A dependency-free NativeAOT WinExe placed at the portable ZIP root. It only starts `app\ConnectOnion.WinUIClient.exe`, keeping the original self-contained WinUI publish and all DLLs together under `app\` |
| `ConnectOnion.WinUIClient.Core/` | yes | via tests | **Every WinUI-free surface of the client**: models, SQLite repositories, notification policy, projections, view models. Targets `net10.0-windows10.0.19041.0` but takes no `Microsoft.UI` dependency, so a headless test host can load it |
| `ConnectOnion.Protocol/` | yes | build | Transport-agnostic protocol library (`net10.0`, no WinUI dependency) |
| `ConnectOnion.Protocol.Conformance/` | yes | yes | Cross-checks C# Ed25519/canonical-JSON signing against a Node.js reference signer (`ref-sign.js`) — this is the CI gate |
| `ConnectOnion.Protocol.LiveTest/` | no | manual only | Console smoke test against a real deployed agent; CI runs it only through an explicit workflow dispatch |
| `tests/ConnectOnion.TrimSmoke/` | no | opt-in | Console harness published **trimmed** that asserts the serialization, persistence and identity paths still work when `JsonSerializerIsReflectionEnabledByDefault` is off. Not xunit — a trimmed self-contained publish has no test host to load into. Run via `scripts/Invoke-TrimAudit.ps1`; see `docs/TRIMMING.md` |
| `tests/ConnectOnion.Protocol.Tests/` | yes | yes | xunit unit tests for `ConnectOnion.Protocol` (wire schema, encoding, event parsing) |
| `tests/ConnectOnion.WinUIClient.UnitTests/` | yes | yes | Headless xunit tests over `Core` (projection, notifications, caches, view models), plus the ArchUnitNET layer-boundary tests |
| `tests/ConnectOnion.IntegrationTests/` | yes | yes | xunit tests against a real SQLite file (schema/migrations, repositories, identity store) |
| `tests/ConnectOnion.WinUIClient.UITests/` | yes | yes | FlaUI (UIA3) real-window smoke tests. The 25 required shell/chat tests run on **every** push and PR; an Explorer-based drag-and-drop diagnostic is explicitly skipped because its source coordinates vary with desktop DPI/layout. Memory/performance/layout probes stay opt-in measurements |

**`ConnectOnion.WinUIClient.Core` is the seam that makes the client testable, and getting a file on the right side of it is the whole game.** The app project can't be referenced by a test project — it drags in the Windows App SDK, which a headless test host can't load — so anything that needs coverage lives in `Core`, which the test projects take an ordinary `ProjectReference` on. **Moving a production file into `Core` is how you bring it under test.** If a file won't move because it pulls in XAML types, that's the signal its logic wants splitting into a WinUI-free class, not that the test project needs the Windows App SDK. Note both projects share the `ConnectOnion.WinUIClient` root namespace, so moving a file across the seam is not a namespace change. `LayoutKeys`/`KeyNames` is the worked example of the split: the key-name table is platform-free and sits in `Core`, while the layout translation P/Invokes `MapVirtualKeyW` and therefore stays in the app.

The boundary is enforced, not just described: `tests/ConnectOnion.WinUIClient.UnitTests/Architecture/LayerDependencyTests.cs` uses ArchUnitNET to fail the build if `Core` takes a `Microsoft.UI` dependency or if `Data` starts depending on `ViewModels`.

The `.sln` lives at `ConnectOnion.WinUIClient/ConnectOnion.WinUIClient.sln` even though it references every other project by relative path (`..\ConnectOnion.Protocol\...`, `..\tests\...`).

**All four test projects are on `xunit.v3` (3.2.2)**, not xunit 2.x, which NuGet marks deprecated
(`Legacy`). The migration needed no test rewrites — only `IAsyncLifetime` returning `ValueTask`
instead of `Task` (6 files), `ITestOutputHelper` moving out of `Xunit.Abstractions` into the root
`Xunit` namespace (2 files), and `TngTech.ArchUnitNET.xUnit` → `…xUnitV3` (1 file). Counts and
coverage came out identical either side of it.

`tests/Directory.Build.props` carries two settings for every test project, both explained inline:
`AppendPlatformToOutputPath=false` (one output path per configuration, so a `-p:Platform=x64` on a
`dotnet test` cannot resolve to a stale assembly) and a `NoWarn` for **xUnit1051**, a v3 analyzer
suggesting `TestContext.Current.CancellationToken` at every call site that takes one — 412 hits,
all pre-dating the rule, and threading it through them is a change of its own rather than a rider
on the migration. It imports the root `Directory.Build.props` explicitly; without that the
nearest-file-wins rule would silently drop the repo's analyzer and audit settings for the tests.

SDK pin: `global.json` sets `"version": "10.0.100"` with `rollForward: latestFeature` (any newer .NET 10 feature-band SDK works).

## Commands

Everything except `ConnectOnion.Protocol.LiveTest` is in the solution; the test projects are also runnable one at a time by `.csproj` path.

dotnet test tests\ConnectOnion.WinUIClient.UnitTests\ConnectOnion.WinUIClient.UnitTests.csproj

`Platform` must be `x64`, `x86`, or `ARM64` for the WinUI project — `Any CPU` doesn't work for packaged debugging. Visual Studio F5 (Debug/x64, Deploy checked for `ConnectOnion.WinUIClient` in Configuration Manager) is the most reliable path for XAML debugging; `dotnet run -p:RunUnpackaged=true` is the fast CLI loop.

CI (`.github/workflows/ci.yml`, `windows-latest`) restores, audits dependencies for known vulnerabilities (`dotnet list package --vulnerable --include-transitive`), builds the `.sln` in Release/x64 with packaging disabled, runs the three headless test projects with Cobertura coverage collection, compiles the UI smoke test, publishes a self-contained ReadyToRun unpackaged build with trimming enabled, uploads coverage, and ends on the Conformance gate. **Trimming is ON for Release as of 2026-08-05**, and `docs/TRIMMING.md` is the gate that decided it — read that before changing `PublishTrimmed` in either direction. The evidence: 0 app-owned IL warnings; source-generated JSON on every serialization path with a trimmed console harness proving them across a real process restart; `scripts/Test-TrimmedRuntime.ps1` proving the **trimmed app** renders a turn written by the **trimmed** harness (tool-activity steps, arguments, results, interactive cards); and the latest nested-layout portable release rehearsal auditing clean at **73.22 MB compressed / 176.85 MB unpacked** against untrimmed baselines of 118.91 / 309.21 MB, with warm start and idle working set both *better* than untrimmed (worst regression +2.9%, budget >10%).

The signed-MSIX criterion was **rescoped, not waited on**: this repo builds no MSIX, so that criterion gated a validated configuration behind validation of a channel that does not exist — and signing attests who published a binary while trimming changes what is in it, so the two were only ever coupled by this document. It is recorded as deferred; run it against a trimmed package before MSIX publishing is ever restored. Two traps worth keeping: the audit's trimmed publish sets `PublishReadyToRun=false`, so **its size and startup are not comparable to the shipping build** (a cold launch takes ~11.8 s purely because everything JITs — always compare R2R against R2R); and the package size baseline was re-ratified with trimming, because an upper-bound gate left at the untrimmed number would have had ~60 MB of slack and caught nothing. `TrimmingGateTests` fails the build if the Release or CI setting changes before then. Two neighbouring runtime switches are settled and should stay settled: **`TieredPGO` is on** (it complements ReadyToRun — R2R code is compiled without knowing what this app does, and PGO re-jits the hot paths against real profile data; it is off by default for R2R code unless set), and **`InvariantGlobalization` must never be turned on** — it would break the zh-CN locale, make `Common/LayoutDirection`'s `CultureInfo.GetCultureInfo` throw, and change every `CurrentCulture` format including the payment amount on an onboarding card. Both facts are asserted by `RenderHotPathContractTests`, and the csproj carries the reasoning inline. `ConnectOnion.Protocol.LiveTest` runs only through an explicit manual workflow dispatch because it depends on a deployed agent; push, PR, and scheduled runs skip it. CI executes the FlaUI shell/chat suite against the published executable on **every** push and PR. `--filter "Category=UiSmoke"` selects **27**, and the run reports **26 passed / 1 skipped** — reconcile that against the 25 real assertions before assuming a test vanished: the skip is the Explorer drag diagnostic, and one of the 26 is `Chat_ManyTurnsInOneConversation_MemoryProbe`, an opt-in memory probe that returns immediately unless `CONNECTONION_MEMORY_PROBE=1`. It counts because it is a partial of `ShellSmokeTests`, which carries the category at class level; the other opt-in diagnostics (`MemoryLeakTests`, `PerformanceAuditTests`, `TrimmedRuntimeTests`) are standalone classes with no category and are therefore invisible to CI. A new opt-in diagnostic belongs in its own class for that reason. Each run uses an isolated data root and uploads its TRX/screenshots unconditionally, since a failing PR is exactly when those screenshots matter. The test steps deliberately omit `-p:Platform` and rebuild rather than passing `--no-build`: the solution build maps the conformance project to `Any CPU`, so forcing the platform through to a standalone `dotnet test`/`dotnet run` sends it looking for output under `bin\x64\...` that the solution never produced — hence the workflow's env var being named `BUILD_PLATFORM` rather than `PLATFORM`, which MSBuild would auto-import as `$(Platform)`. There is a comment in the env block about exactly this. **For the test projects that trap is now also fixed at the source**: `tests/Directory.Build.props` sets `AppendPlatformToOutputPath=false`, so a `dotnet test` that does pass `-p:Platform=x64` resolves to the same `bin\<Configuration>\` assembly as everything else and cannot pick up a stale copy. It had already produced two wrong answers — a bogus single failure naming an `AutomationId` absent from the source, and an integration suite reported as 92 tests when it has 164.

The coverage gate merges production lines across the three reports and is a **ratchet, not a fixed
threshold**: `coverage-baseline.json` holds the high-water mark per assembly and a run fails when
coverage drops below it by more than the tolerance (0.25pp, which absorbs run-to-run noise in
timing-dependent paths). Coverage that rises passes and prints the new figure; advancing the
baseline is a deliberate `-UpdateBaseline` commit, never something CI does. The `-*Floor`
parameters are a separate absolute minimum that `-UpdateBaseline` cannot sink below, so a slow
drift downward still has to cross a line that shows up in review. Generated code and test
assemblies are excluded.

Two fixed thresholds (86.0%/88.5%) preceded this and had to go: they sat 3 and 6 lines above the
measured values, so any change adding an uncovered branch broke CI — which pushes a contributor
toward a padding test or a quietly lowered number rather than toward better tests.

**The gate also prints what it cannot measure.** `ConnectOnion.WinUIClient` (~23.7k source lines of
C# plus ~9.5k of XAML) appears in *no* coverage figure and cannot: a headless test host cannot load
the Windows App SDK, and the FlaUI suite runs the app out-of-process where coverlet's in-process
collector does not follow. Absent and 0% look identical in a report listing only what it measured,
so the size of that blind spot is stated explicitly. Those are physical source lines and are **not**
comparable to the sequence-point counts in the table — they say how much is out of scope, not how
much is untested.

There is no lint/format command configured for this repo.

## Local data

SQLite at `%AppData%\ConnectOnion\connectonion.db` when run unpackaged (`dotnet run`), or under `%LOCALAPPDATA%\Packages\ConnectOnion.Desktop_<publisher hash>\LocalState\ConnectOnion\` when run packaged/installed/deployed from Visual Studio. WAL journal mode, foreign keys on. **That folder name is derived from the package identity (`Name` + `Publisher`), which is why neither can ever change** — a package with a different pair installs beside the old one and cannot see its data, silently. See `docs/RELEASE.md`.

`AppStorage` selects that deployment-specific root explicitly: `ApplicationData.Current.LocalFolder`
when package identity exists, `%AppData%` otherwise, and `CONNECTONION_DATA_ROOT` for isolated
automation. On the first packaged launch it moves data left by pre-release builds from virtualized
`LocalCache\Roaming\ConnectOnion` into `LocalState\ConnectOnion` before opening SQLite.

**Schema changes go through `Data/SchemaMigrator.cs` — `CREATE TABLE IF NOT EXISTS` alone cannot evolve a table that already exists.** `AppDatabase.EnsureInitializedAsync` first ensures the baseline (`CreateSchemaAsync`), then steps any older database forward. The version lives in SQLite's own `PRAGMA user_version` (a header integer: no table needed, no query cost, and written inside the same transaction as the migration it records) — not in `app_meta`. To add a column: append one `Migration(n, sql)` to `SchemaMigrator.Migrations` and bump `LatestVersion`; never edit or renumber a released migration, because databases in the wild have already recorded running it. Each migration runs in its own transaction, so schema change and version bump commit together or not at all. `user_version == 0` means "never versioned": missing baseline columns are repaired and a pre-`messages` `conversations.envelope_json` store is imported into normalized message rows inside one transaction, then the database is stamped as version 1. The legacy blob table is retained as recovery evidence. A database at a version *newer* than this build throws rather than running against a shape it doesn't understand. Deleting the `.db` file still works to reset dev state, but it is a convenience — no longer the upgrade path.

Schema v8 adds the `message_search` FTS5 table with the trigram tokenizer plus triggers that mirror user/agent transcript content. Global transcript search must query that index, never return to a leading-wildcard `LIKE '%…%'` scan. The index stores the stable `(conversation_id, message_id)` pair and joins back through the messages primary key; do not couple it to SQLite's mutable implicit `rowid` **of `messages`**. Trigram lookup needs at least three characters, so shorter global-search input matches session and agent metadata only.

Schema v11 adds `sessions.unread_count` and `sessions.requires_attention`. Notification policy marks them only when the user is not already viewing that conversation; opening the chat clears both. A completed turn clears stale approval attention while preserving/incrementing unread state, because an approval is no longer actionable once the turn has finished.

**v9 is what makes maintaining that index affordable, and the trap it fixes is worth understanding before touching the triggers.** `conversation_id`/`message_id` are `UNINDEXED` columns on an fts5 table, and a non-`MATCH` constraint on an fts5 virtual table has **no index at all** — `EXPLAIN QUERY PLAN` reports `SCAN message_search VIRTUAL TABLE`. v8's triggers deleted by that pair, and the trigger is per-row, so `DELETE FROM messages WHERE conversation_id = ?` cost O(the conversation's messages × every message in the database): measured at **1.03 s** to delete a 500-message conversation from a 20k-message database, against **0.003 s** after. v9 adds `message_search_map` — an ordinary table keyed `fts_rowid INTEGER PRIMARY KEY` with a unique index on `(conversation_id, message_id)` — and the triggers now address the FTS row by `rowid`, which fts5 *does* seek directly. The insert trigger writes the map row first so `last_insert_rowid()` supplies the id the FTS row is then given explicitly; both statements share one condition so the two tables cannot drift apart. **This is not the forbidden rowid coupling**: the stored rowid is the one we assign to the *FTS* row, `messages.rowid` is still never read, and `(conversation_id, message_id)` remains the only thing identifying a message. The migration rebuilds the index rather than back-filling, because v8 rows were given implicit rowids that were recorded nowhere. `ConversationRepositoryTests.TranscriptSearchIndex_IsMaintainedByRowid_AndStaysAlignedAcrossEdits` pins the query plan — the correctness half alone would pass against the scanning form.

v10 adds two indexes that exist only for statements nothing names explicitly, so nothing else would notice their loss: `ix_trace_events_execution` (`DeleteExecutionAsync` removes traces by `execution_id`, which was a full scan of `trace_events` on a user-facing cancel) and `ix_sessions_order`, which covers `SessionRepository.LoadAsync`'s `ORDER BY sort_order, updated_at DESC, id` — `ix_sessions_agent_updated` leads with a different column, so that load ran a full scan plus a temp B-tree sort on **every sidebar refresh**. `AppDatabaseSchemaTests` asserts both exist and that the planner actually chooses the ordering one.

`AppDatabase.OpenAsync` sets **`PRAGMA synchronous = NORMAL`** per connection. Unlike `journal_mode`, which lives in the file header and is genuinely once-per-database, `synchronous` is a property of the *connection* and resets to `FULL` on every open — so it belongs in `OpenAsync`, not beside the WAL line in `EnsureInitializedAsync`. `FULL` fsyncs on every commit, and nearly every write here is its own transaction (a turn's messages, a rename, a preference, a pin), so that was an fsync per user action; 200 separate commits measured 53 ms at `FULL` against 4 ms at `NORMAL`. `NORMAL` is the documented companion to WAL — a commit still survives a process crash, only an OS crash or power loss can cost the last few. `foreign_keys` moved into the **connection string** (`SqliteConnectionStringBuilder.ForeignKeys`) so this stays the connection's *one* setup statement rather than a second round trip on every repository call.

Tables: `app_meta`, `agents` (incl. `icon_path`, schema v6 — the user's chosen avatar, a path relative to the data root, never the image bytes), `sessions` (incl. `mode`, schema v3; `has_custom_title`, schema v7; and unread/attention state, schema v11), `preferences`, `messages` (one row per chat bubble, not a JSON blob), `message_attachments` (attachment **metadata only**: kind/filename/mime/size/cache-path — never the base64 payload), `executions`, `trace_events`, `identity_keys` (`private_seed` and `mnemonic` (schema v5) are DPAPI-protected (`CurrentUser` scope) blobs, base64-encoded — never plaintext), `usage_events` (schema v2), `message_search` (schema v8), and `message_search_map` (schema v9).

**The agent list is deliberately *not* paged.** Agents are added one at a time, each needing an address and an onboarding step, so the list is bounded by deliberate user action where conversations accumulate as a byproduct of chatting — measured, 200 agents load in 0.6 ms against 225 ms for 20,000 conversations. What agent count *does* cost is the presence sweep (see above) and `info_json`, and neither is a paging problem. **`AgentRepository.LoadSummariesAsync` is the read for surfaces that only name, draw and reach an agent** — the sidebar refresh, the tray menu, the search catalog — because `LoadAsync` selects the whole cached `/info` response (skills and descriptions, a couple of KB each) at thirteen call sites of which four ever read it. It returns `AgentSummary`/`AgentSummaryState`, **not a blob-less `AgentConfig`**: `SaveAsync` writes `info_json` from the object handed to it and five production call sites round-trip a load straight back into it, so a partial `AgentConfig` would erase every agent's cached metadata. Same principle as `SessionPage` below — the type makes the mistake unrepresentable instead of merely discouraged.

**`SessionRepository.SaveAsync` reconciles the entire index and nothing in the app calls it any more.** It upserts every session handed to it and deletes every row that is not, so passing it a subset — a page, a filter, one agent's conversations — destroys the rest silently. It survives only as a test seeding helper, where "these are all the sessions there are" is true by construction. Production reads are targeted (`GetSessionAsync`, `CountForAgentAsync`, `LoadAgentSessionsAsync`, `LoadRecentAsync`, `LoadPinnedAsync`, `SearchByTitleAsync`, `ListSessionIdsForAgentAsync`, `GetActiveSessionIdAsync`) and production writes are targeted too (`AppendSessionAsync`, `UpdateSessionAsync`, `SetPinnedAsync`, `DeleteSessionAsync`, `DeleteSessionsForAgentAsync`). **Reaching for `LoadAsync` and then a `FirstOrDefault` reads every conversation the user has ever had to find one** — that was six call sites, plus two that loaded the whole index to compute the integer `SessionSummary.NewConversation` numbers from (hence its `int` overload). Two whole-index consumers remain and are legitimate: the tray's "More" submenu documents itself as listing the full remainder, and the session-search overlay filters the whole title catalog on the keystroke. **Paged reads return `SessionPage`, which deliberately has no path into `SaveAsync`** — the type is what prevents the partial-list footgun, not a comment.

`LoadAgentSessionsAsync` is keyset paginated on `(updated_at, id)`, never `OFFSET`: a conversation jumps to the front the moment a message lands in it, and under OFFSET that shifts later rows up so the next page skips one entirely. A keyset cursor can at worst repeat a row that moved, which in a navigation tree is a cosmetic duplicate rather than a conversation the user cannot reach. `id` is in the cursor because `updated_at` ties. `ResolveForAgentAsync` is the SQL twin of the pure `SessionSelection.FindExisting` (active-conversation-wins-if-same-agent, else the agent's most recent); `SessionRepositoryTests.ResolveForAgentAsync_AgreesWithSessionSelection` holds the two to the same answers so the rule cannot exist in two drifting copies.

Deleting a conversation is **not** an FK cascade — the children are deleted explicitly, in order (`ConversationRepository.DeleteConversationAsync` → attachments + messages; `DeleteExecutionsAndTracesAsync` → traces + executions), and only then does `SessionRepository.SaveAsync` remove the `sessions` row. The FKs declare no `ON DELETE`, so getting that order wrong raises a constraint violation that the repositories' `try/catch` swallows into a log line. Keep the order.

**Conversation titles.** A new conversation gets a "Conversation N" placeholder (`SessionSummary.NewConversation`) which its first message replaces, and which the user can override from the sidebar's Rename. Whether a title is *still* the placeholder is the stored `sessions.has_custom_title` flag (schema v7) — **never a pattern match on the title text**. It used to be `^Conversation \d+$` in two view models, which made the placeholder untranslatable (a localized one stops matching, so that conversation keeps its placeholder forever) and rename unsafe (a user title that happened to match would be overwritten by the next message). `SessionSummary.TryApplyTitleFromPrompt`/`TryRename` are the only two things that set it, and the v7 backfill reproduces the old predicate exactly so existing rows keep their current behaviour. Core has no resource map, so the placeholder's *wording* is passed in from the app (`Common.SessionTitles.PlaceholderFormat`); the flag, not the wording, is what the logic reads.

`usage_events` is the **token-usage ledger** and is the deliberate exception to all of the above: it has **no foreign key** and is **never** touched by conversation or agent deletion. Usage records that tokens were *spent*, which stays true after the chat is gone; a cascade would make the Usage panel's totals silently shrink whenever a user tidies their sidebar. `conversation_id`/`agent_id` are therefore allowed to dangle (they exist only for drill-down, which must `LEFT JOIN` and tolerate a miss), and `agent_name` is snapshotted at write time so a deleted agent's rows can still be labelled. The only code path that ever deletes from it is `UsageRepository.ClearAsync`, reached solely from the explicit, confirmed "Clear usage history" button in Settings → Usage.

**SQLite here is `winsqlite3` — the copy that ships with Windows — and it is built without local-time support.** `date(…, 'localtime')` returns **NULL**, so a query grouping on it yields no rows at all and the caller's `try/catch` turns that into a silently empty panel rather than an error. Convert to local time by arithmetic instead: `date((created_at + $offset_ms) / 1000, 'unixepoch')` with the offset passed as a parameter, which is what `UsageRepository.GetDailyTotalsAsync` (the heatmap's per-day aggregation) does. One offset covers the whole window, so a call within an hour of midnight can land in the neighbouring day across a DST boundary — accepted deliberately; carrying historical offsets would need a time-zone table SQLite does not have.

`IdentityStore` distinguishes *nothing stored* (first run → generate quietly), a historical plaintext seed, and *stored but unreadable* (for example a copied `.db`, restored profile, or corrupt protected blob). An exact 64-hex-character pre-DPAPI seed is decoded, checked against its stored address, and rewritten with DPAPI without changing the identity. An unreadable protected value still regenerates — there is nothing to recover — but it is **not silent**: it raises `IdentityStore.IdentityReset`, latches `WasReset`/`ResetReason`, and `MainWindow` surfaces an error toast, because the app's address changes and every agent that authorized the old one must authorize the new one. Do not weaken the address check or collapse these paths together.

**DPAPI is what keeps the database safe and also what makes it useless as a backup** — a copied `.db` or a new machine cannot decrypt the seed. So a new identity is minted from a BIP39 phrase (`AgentIdentity.GenerateWithMnemonic`) and the phrase is stored beside it, DPAPI-protected the same way; `IdentityStore.ExportBackup`/`ImportMnemonic`/`ImportSeed` and Settings → Identity are the user-facing half, and `NewlyCreatedMnemonic` is a latch (like `WasReset`) that `MainWindow.RevealNewRecoveryPhraseIfAny` shows once, because the identity is usually created before a window exists. **The derivation is a cross-client contract, not an implementation detail**: `ConnectOnion.Protocol/Bip39.cs` matches the Python SDK's `address.py` and oo-chat's `use-identity.ts` byte for byte (PBKDF2-HMAC-SHA512, 2048 rounds, salt `"mnemonic"`, first 32 bytes of the seed used directly as the Ed25519 seed — no BIP32/SLIP-0010 path), so the same phrase restores the same `0x` address in all three. `Bip39Tests` pins it against vectors generated by those references; changing any of it silently breaks every written-down phrase. Identities created before schema v5 have `mnemonic IS NULL` forever — nothing can derive a phrase for an existing seed, and regenerating one to give it a phrase would change the address every agent already authorized, so those back up via their raw seed instead. `ImportMnemonic`/`ImportSeed` raise `IdentityReplaced`; the caller must drop every live socket (they authenticated as the old address) and the restore UI refuses while a run is active.

Image cache for received `agent_image` attachments lives under the selected app-data root at `cache\images\`, filenames are the content's SHA-256 hash (never trust a remote-provided filename).

**Agent icons** live under the same root: committed ones in `avatars\`, and a pick that has not been saved yet in `temp\avatars\`. `agents.icon_path` stores the *relative* form (`avatars/agent-….png`) so a portable install that moves folders keeps resolving its own icons, and every read goes through `AppStorage.GetAgentIconAbsolutePath`, which refuses a path that escapes `avatars\` — that column is hand-editable, and the same resolution guards the delete paths. Committed filenames carry a GUID, which is what lets "commit the new file, save the row, then delete the old one" be safe: the file just written can never be the one being deleted. **`AppStorage.PurgeTemporaryAgentIcons` is startup-only and must never be called from `EnsureDirectories`** — the picker calls that while an Add Agent form is open, so purging there would delete the icon the user is about to save.

## Architecture

### Protocol layer (`ConnectOnion.Protocol`)

Deliberately has zero WinUI/platform dependency so it's unit-testable headless. This is where wire-format logic belongs — don't duplicate JSON parsing in the WinUI layer.

- **`AgentConnectionService`** — the WebSocket state machine (C# port of the TS SDK's `remote-agent.ts`): opens/authenticates via `CONNECT`→`CONNECTED`, sends `INPUT`, resolves on `OUTPUT`. Interactive turns (`ask_user`, `approval_needed`, `plan_review`) and onboarding are surfaced as dedicated C# events, not lumped into the generic stream; everything else (`thinking`, `tool_call`, `tool_result`, `llm_call`, `llm_result`, `assistant`, `agent_image`, `intent`, `eval`, `compact`, `tool_blocked`, `files_received`) is forwarded as a generic `StreamEvent` carrying the raw JSON for the ViewModel to interpret. A 60s silence watchdog is the only bounded wait — `ask_user` legitimately pends on a human indefinitely.
- **`WireMessage`** — thin `JsonElement` wrapper (`GetString`/`GetBool`/`TryGet`), not raw `JsonDocument.Parse` scattered around. Outgoing messages are plain `Dictionary<string, object?>` (no source-gen context, no attribute-based DTOs) — follow this convention for new message types rather than introducing typed request/response classes.
- **`WireJson`** — serializes those dictionaries, and **is the only way an outgoing frame reaches the socket**. Never `JsonSerializer.Serialize(dict)`: `PublishTrimmed=true` sets `JsonSerializerIsReflectionEnabledByDefault=false`, so the reflection serializer *throws* rather than merely risking a trimmed member, and this call site covers every frame the client sends. It is a hand-written `Utf8JsonWriter` (sibling of `CanonicalJson`, which does the same for signing with the relaxed encoder), byte-identical to the reflection serializer's output — insertion order, default escaping, no indentation — and its `WriteValue` throws on an unrecognised value type rather than guessing, so a builder putting something new on the wire fails in `WireJsonTests`. **Two sanctioned JSON mechanisms exist and there is no third:** a source-generated context (`AppJsonContext`, `ConversationJsonContext`) for blobs we define and read back out of our own database, and `WireJson`/a hand-written `Utf8JsonWriter` for shapes the host defines. See `docs/TRIMMING.md`.
- **`InputMessageBuilder`** — pure function building the `INPUT` frame dict; kept separate from `AgentConnectionService` specifically so the exact wire shape (text-only / images / files / mixed) is unit-testable without a live socket.
- **`AttachmentModels`** — `DataUrlCodec` (encode/decode `data:` URLs, and the size-limit math replicated from the Python host's `validate_files`: the server measures the **encoded string length**, not raw bytes, so client-side preflight must too) and `AttachmentWireEvents` (typed parsers for the real `agent_image`/`files_received` wire events — see "Multimodal attachments" below for the full protocol contract).
- **`EndpointResolver`** — relay lookup, cached `/health` reachability probing, and separately cached `/info` fetch/parsing (`AgentAcceptedInputs`/`AgentFileInputs` capability model).
- **`AgentIdentity` / `CanonicalJson` / `Hex`** — Ed25519 identity and canonical-JSON signing, verified byte-for-byte against `ref-sign.js` by the Conformance project.

### Core layer (`ConnectOnion.WinUIClient.Core`)

The client's logic, minus everything that needs a window. It references `ConnectOnion.Protocol` and takes only headless packages (`CommunityToolkit.Mvvm`, `Microsoft.Data.Sqlite.Core`, `Microsoft.Extensions.Logging.Abstractions`, `System.Security.Cryptography.ProtectedData`); the app project references *it*. Everything the "Local data" section above describes (`Data/`: `AppDatabase`, `SchemaMigrator`, the repositories, `IdentityStore`) lives here, along with `Models/`, `Services/Notifications/`, `Services/Runtime/` (`AgentSessionManager`, `AgentTurnExecutor`, `ChatTurnProjection`, `AgentConnectionRegistry`, the projectors), `Services/Attachments/` (validation + encoding, incl. `AttachmentImageCacheService`), `ConversationCache`, and the WinUI-free view models.

`AgentSessionManager` and its two companions live here rather than in the app project, and the
reason is worth keeping: they have no WinUI dependency and never did, but they sat on the app side
where no headless test host can load them — so the single most critical component in the client
(connections, turn lifecycle, the persist-before-terminal-state ordering) had no behavioural test
at all and was outside the coverage gate entirely. The one thing holding them there was three
calls to the static `AppServices.Notifications` locator; the coordinator itself was already in
Core, so it became a constructor parameter (`NotificationCoordinator?`, optional — null means
"nothing is listening", which is a headless test's situation, not a degraded mode). Behavioural
cover is `tests/ConnectOnion.IntegrationTests/Runtime/AgentSessionManagerTests.cs`. The socket half
still needs a fake agent and remains uncovered.

Note `ConnectOnion.WinUIClient.Core/Properties/AssemblyInfo.cs` grants `InternalsVisibleTo` to the
**app project**, not only to the two test projects. Core and the app share the
`ConnectOnion.WinUIClient` root namespace, so a file that moves across the seam looks unchanged at
every call site — but its `internal` members silently stop reaching the app. The grant is what
keeps "move a file into Core to bring it under test" a pure move instead of one that also forces
every internal member it exposes to become public. It is one-way: Core still cannot see the app,
which is what the ArchUnit layer gate enforces.

It still targets `net10.0-windows10.0.19041.0` rather than plain `net10.0` — it needs Windows-only APIs like DPAPI — but that is *not* a licence to reach for `Microsoft.UI`; the ArchUnit test named above is what stops it. Anything that must touch a `Window`, a `DispatcherQueue`, a picker, or a XAML type belongs in the app project instead.

### WinUI client (`ConnectOnion.WinUIClient`)

**Folder layout.** The project root holds only `App`, `Program`, and the `MainWindow.xaml`/`.xaml.cs` pair; every other `MainWindow` partial lives in `Shell/` (see `Shell/README.md`). `Controls/` is grouped by surface — `Chat/`, `Agents/`, `Settings/`, `Shell/`, `Primitives/` (see `Controls/README.md`). **Both folders deliberately keep the namespace they had before the grouping** (`ConnectOnion.WinUIClient` and `ConnectOnion.WinUIClient.Controls` respectively), so folder ≠ namespace here and that is intentional, not drift: a partial class can only have one namespace, and a control's namespace is what 17 XAML files name in their `xmlns` and what each `x:Class` must match. Nothing enforces folder/namespace agreement in this repo (`Directory.Build.props` sets `EnforceCodeStyleInBuild` but IDE0130 is not on), so grouping stays free. `Primitives/` carries one rule: no view-model or feature-model references.

`Program` combines Windows AppLifecycle redirection with a named mutex derived from
`AppStorage.RootDir`. AppLifecycle handles ordinary second activation of the same installed or
unpackaged executable; the data-root mutex also prevents two portable versions extracted to
different folders from opening the same SQLite and identity store. Isolated automation roots get
different mutex names and can still run side by side.

Shell-owned full-window modals are deliberately absent from `MainWindow.xaml` at startup. `Shell/MainWindow.Overlays.cs` creates Settings, shortcuts, About, agent-add, and session-search controls on first use, wires their lifetime events, and adds them to `FloatingOverlayLayer`. Keep these surfaces lazy: constructing the settings tree before first frame loads view models and native XAML surfaces the user may never open.

**Window placement and scale** (`Shell/MainWindow.Placement.cs`, `Shell/MainWindow.ViewMenu.cs`). The persisted placement is position + maximized + **size** (`WindowPlacementPolicy` serializes 5 comma-separated fields; 2- and 3-field rows from older builds still parse and simply carry no size). Restore **resizes before moving** — the work-area clamp measures against the window's size, so growing it afterwards can push it back off-screen — and both the saved position and the saved size are the *restored-state* ones, so exiting while maximized reopens maximized but un-maximizes to what the user last chose. `OverlappedPresenter.PreferredMinimum*` takes **device** pixels while the layout works in epx, so the 640×480 floor is multiplied by the window's DPI; unscaled it would be only 400 epx at 160%.

Three separate scales act on this window and they are not interchangeable. **DPI** is the platform's. The **user's zoom** (Ctrl +/-, 0.67–2.0, persisted) applies to the content area, the overlay layer and the toast host — siblings of each other, so all three need the transform explicitly. The **OS text scale** (`Services/TextScaleService` over `UISettings.TextScaleFactor`, applied by hand because WinUI 3 does not implement `IsTextScaleFactorEnabled`) multiplies into that as `EffectiveContentScale`, *and* additionally scales the title bar, which the user's zoom deliberately does not — Windows draws the caption buttons beside it and follows the system setting, so zooming only the app's half would leave one title bar at two sizes. Above 120% the window asks for a `Tall` caption to match. The caption-button column is sized from `AppWindowTitleBar.RightInset` (`LeftInset` under RTL); the `144` still in the XAML is only the pre-measurement fallback.

**`EffectiveContentScale` is the one definition of logical width, and every caller must use it** — `RootGrid_SizeChanged` and `EffectiveContentWidth` both feed `SidebarLayoutPolicy.IsCompactWindow`, and when one of them used the zoom alone a resize and a navigation reached opposite conclusions about the sidebar above 100% system text. **`SizeChanged` fires per frame during a window drag**, so it is a hot path: the title bar's metrics (caption inset, scaled column width) are guarded by `_titleBarMetricsValid` rather than recomputed there — nothing about them depends on the window's *size* — and the DPI behind them is cached in `_cachedDisplayScale`, invalidated from `XamlRoot.Changed` because `AppWindow` has no DPI event. `ApplyZoomTo` likewise returns before allocating in the identity case, which is what most users are in most of the time. `RenderHotPathContractTests` pins all of this.

MVVM via **CommunityToolkit.Mvvm** (8.4.2) source generators — models/view models are `partial` classes deriving from `Common/ObservableObject.cs`, a thin bridge over `CommunityToolkit.Mvvm.ComponentModel.ObservableObject` (kept as a named base so the many `: ObservableObject` declarations need no churn, and so the generators run on subclasses). `[ObservableProperty]` is applied to **partial properties** (`public partial T Foo { get; set; }`), not backing fields — this is the WinUI/CsWinRT-recommended form and keeps the build free of the `MVVMTK0045` AOT advisory (no suppression). Because a partial-property declaration can't carry an initializer, **non-null defaults are seeded in the constructor**; a `{ get; private set; }` accessor list preserves read-only-to-XAML encapsulation. Use `[NotifyPropertyChangedFor]` for derived properties, `partial void On<Prop>Changed` hooks for setter side-effects, and `[RelayCommand]`/`[NotifyCanExecuteChangedFor]` for commands. Attributes that must land on the property (JSON, etc.) go **directly on the partial property** (no `[property: …]` target). Keep a property hand-written (still calling the inherited `SetProperty`) only when its setter must *transform* the incoming value — `SessionSummary.Mode` normalizes to a valid mode — which `[ObservableProperty]` deliberately can't express. **Dependency injection** is the .NET **Generic Host** (`Microsoft.Extensions.Hosting`): `App` builds an `IHost` in its constructor, all singletons + view models are registered in `Services/ServiceRegistration.AddAppServices`, and `App.Services` is the composition root. **View models take their dependencies as constructor parameters** and are registered `Transient` — a page obtains its one via `App.GetService<XyzViewModel>()` in its ctor, because WinUI instantiates pages/controls/windows itself (parameterless ctor, `Frame.Navigate`), never through the container. `Services/AppServices.cs` is a typed accessor over `App.Services` (get-only static properties) that framework-created **code-behind** uses to reach shared singletons — the DI boundary WinUI's view model imposes, not a service-locator by choice. Startup wiring runs as `IHostedService`s after storage initialization: `StartupStateService` reads preferences, language, placement, shortcuts, and notification settings in one SQLite snapshot before `NotificationStartupService` consumes them. `ILogger<T>` is available to any injected type. Register a value-transforming or two-same-type-parameter service with a factory lambda (see `NotificationCoordinator`); everything else is auto-wired.

The shared `HttpClient` is **resilient via Polly** (`Microsoft.Extensions.Http.Resilience`): `ServiceRegistration` registers a named client (`"agent"`) with an `AddResilienceHandler` pipeline — `AddRetry` (2 attempts, jittered exponential backoff) then `AddTimeout` (10s per attempt) — and the singleton `HttpClient` is that named client from `IHttpClientFactory`. Every agent HTTP call inherits it with no call-site code: `/health` presence probes, detail-page `/info` fetches, the relay lookup `EndpointResolver` makes with the passed client, and agent-image downloads all flow through this one client. **No circuit breaker on purpose** — a presence probe must keep retrying a flaky agent, not latch it "offline" until a breaker half-opens — and callers already impose their own overall timeouts, so the pipeline only adds retries within that budget. `ConnectOnion.Protocol` stays Polly-free: it receives the already-resilient `HttpClient` as a parameter.

**Presence probing is pull-based, not a timer.** `AgentPresenceService` answers from a per-agent TTL cache and the sidebar sweeps it on refresh — which happens on every navigation — so the cost is driven by how much the user moves around, and a minimized window probes nothing. **The sweep is bounded at `MaxEagerPresenceProbes` (32) and the tail is probed on realization** (`ItemsRepeater.ElementPrepared` → `AgentRow_ElementPrepared`): each probe is an HTTP call with a retry pipeline, re-armed every 30 s while an agent reads offline, so an unbounded sweep over a few hundred agents generated requests for rows nobody could see faster than four-at-a-time could retire them. The cap sits well above what anyone accumulates by hand, so a real sidebar behaves exactly as before — every agent probed, online count complete on first paint. It is deliberately *not* "probe only what is visible": one expanded branch of 25 conversations pushes the other agents below the fold, and their status dots going blank because a conversation list is long would be a regression. `EnsureCheckedAsync` has an `(agentId, address, directUrl)` overload because those three values are all a probe uses — requiring a whole `AgentConfig` is what made callers read every agent, and every agent's cached `/info` blob, to ask whether one was reachable. Two things keep that from becoming a stream of HTTP: the `Online` TTL is **5 minutes** (a short one turned ordinary page-to-page movement into a request per agent per minute, each with two Polly retries; an agent that went down is discovered when the user actually sends, which is the case that matters), while `Offline` stays at 30s because that is the transition someone is waiting on. And the sweep is a plain `foreach`, so `MaxConcurrentProbes` caps it at four in flight — otherwise a dozen agents all probe at once. `Checking` is published *before* queueing, so a large sweep does not leave most rows looking untouched.

- **Pages own their ViewModel** as a `public XyzViewModel Vm { get; } = App.GetService<XyzViewModel>();` property (resolved from the container — see the DI note above); XAML uses `x:Bind` against `Vm.*`, code-behind wires routed events (`Click`, `PointerEntered`, etc.) that call `Vm` methods. **Large types are split into partial-class files named `Type.Aspect.cs`, and that is the repo's standard answer to a file growing past ~500 lines** — not a new class, not regions. `ChatViewModel` is `ChatViewModel.cs` (state, properties, conversation load/restore, `IChatProjectionTarget`), `.Run.cs` (send/stop/mode and folding run snapshots into the list), `.Conversation.cs` (new/branch/retry — the operations that re-point the run subscription), and `.StreamEvents.cs` (stream-event → `ChatMessage` mapping, interactive-turn bubbles, per-turn token/duration aggregation). `ChatPage` is `ChatPage.xaml.cs` (lifecycle, navigation, load) plus `.Scrolling.cs` (scroll/stick-to-bottom/load overlay — the timing-sensitive part), `.MessageActions.cs`, `.Attachments.cs`, `.Interactive.cs`, and `.Find.cs`. The same idiom carries `ConversationRepository.Mapping.cs` (row↔object SQL plumbing, split from the public repository API) and `ChatTurnProjection.Events.cs` (the per-event-type dispatch table — **this is the file to edit when the agent gains a new event type**).
- **The run runtime owns connections and turns, not pages** (`Core`'s `Services/Runtime/`): `AgentSessionManager` (app-level in *lifetime* — a DI singleton reachable through `AppServices` — but a `Core` type, so it is headlessly testable) holds the per-conversation WebSockets (`AgentConnectionRegistry`) and drives each turn through the headless `ConversationRunRegistry`. It persists the user message on send, buffers the run's stream events, and — when the reply lands — projects them into bubbles and writes them *before* publishing the run's terminal state, so a page opened mid-turn loads history from SQLite and replays the live events on top instead of double-rendering them. A `ChatPage` only ever `Subscribe`s; closing it does not cancel the turn, and a turn completes (and notifies) with no page open at all. `ChatTurnProjection` is the single stream-event → `ChatMessage` mapping, driven identically by the live view model (`IChatProjectionTarget` over the `ObservableCollection`) and by the headless persist path (over a plain list) — put new event handling there, never in one of the two callers.
- **Chat list rendering and caches**: `ChatPage.xaml` has one `DataTemplate` per bubble kind dispatched by `Common/ChatMessageTemplateSelector` — don't collapse them back into a single template that builds every bubble variant and hides all but one with `Visibility`, which is what made scrolling expensive. Conversation restore loads the newest 160 rows and prepends older pages near the scroll boundary; `ObservableRangeCollection` raises one reset for each bulk restore/prepend instead of one layout pass per bubble. `Services/ConversationCache` keeps up to the last 4 *idle* conversations in a real LRU, also capped at an estimated 16 MiB, and remembers whether older rows remain. It is invalidated when a session/agent is deleted and never used for a conversation with an active run — that must load the authoritative persisted history. Cached messages must never retain live `ApprovalResponder` delegates: those instance-method callbacks point back to the page's transient `ChatViewModel`, so cleanup clears them before releasing the message list. `Common/LocalPathToImageSourceConverter` decodes attachment thumbnails at the 280px the templates render at and keeps only weak `BitmapImage` references by path, because virtualization re-runs the converter for the same paths but the cache must not own decoded native surfaces after a page exits. `MarkdownTextBlock` caches on both sides of its work: the parsed `MarkdownDocument` keyed on the source string (a find keystroke or a theme flip re-renders without changing the markdown), **and one `WinUiMarkdownRenderer` per control**, re-armed via `Reset` rather than rebuilt — constructing one registers seventeen object renderers and runs the Markdig pipeline setup, and a recycled row re-renders. Reuse is only safe because the renderer's one fixed field is that control's own `RichTextBlock`; `Reset` must clear **`_matchIndex`** in particular, since it counts search hits during a pass and decides which gets the "current match" styling — carry it over and the highlight silently lands on the wrong occurrence.
- **A `UserControl` that wraps a text element must never forward a null `Foreground` to it.** `UserControl` has no default style, so `Control.Foreground` is **null** unless the caller sets it — and a null `Brush` is not "unset", it means *do not paint*. `MarkdownTextBlock` and `HighlightedTextBlock` therefore sync it by hand (`Foreground ?? ThemeBrushResolver.Resolve("TextPrimaryBrush")`, re-run on `ActualThemeChanged`) instead of binding it. This shipped as every markdown body outside `ChatPage` rendering completely blank — the plan card, the plan-section dialog and the tool log all omitted `Foreground`, `ChatPage` happened to set it, and the symptom pointed nowhere near the cause: text appeared *only while selected* (the selection layer draws its own foreground) while inline code and emoji stayed readable throughout (the renderer gives those an explicit brush). `WinUiMarkdownRenderer` also copies `_target.Foreground` onto each table cell, which is only safe because of that sync. `TextControlForegroundTests` pins it.
- **Interactive card disclosure** (`InteractiveCard`): the whole header is a transparent `Button` that folds the **body only** — the footer stays, so folding a plan you are still being asked about parks the prose without hiding Approve/Reject. `CanCollapse` is `ShowBody`, so a card with nothing to disclose shows no chevron and is not a tab stop. The fold state lives on `ChatMessage.IsInteractiveCardExpanded`, **not on the control**: these cards sit in a virtualized `ListView`, so control-held state would fold whichever unrelated card later reused the container (same reason `ToolActivityViewModel` owns its own `IsExpanded`). It defaults to true — a card that appeared folded would hide a question the agent is blocked on. `DiffPreviewCard` deliberately does **not** bind it: that card already owns a "View changes"/"Hide changes" toggle over the same content, and a second disclosure would let the header hide the button that unfolds it.
  **A card must pass `ChromeTone`/`IconTone`, or every state looks the same.** Both default to `Neutral`, which draws no rail and a grey badge — so `PlanReviewCard`, which passed neither, rendered an approved plan, a rejected one and one still blocking the agent identically. `Message.PlanChromeTone`/`PlanIconTone`/`PlanIconGlyph` mirror the `AskUser*` ones. Its subtitle is `PlanReviewSubtitle`, which empties once the card settles — a header line that reads "The agent will not execute until you respond" is a claim about the present, and a resolved card kept making it.
  Note the badge and the footer line come from **two** properties over the same row (`InteractiveStateLabel` and `InteractiveStateDescription`), and both fall back through the `Historical*` pair when a card is replayed from storage. Both fallbacks must read `Status`: only the label did, so a rejected plan showed a **Rejected** badge directly above "This request has been completed."
- **Sidebar visibility is never changed by navigation.** Opening a conversation used to auto-collapse the sidebar at the compact width; that was removed by request. The remaining `SetSidebarVisible(false)` call sites are all either an explicit user action (the backdrop tap, dragging or key-stepping the resize handle to zero) or the responsive collapse in `RootGrid_SizeChanged` when the *window* crosses the compact breakpoint — which is a layout change, not a navigation. The accepted consequence is that at the compact width the sidebar stays open over the conversation it just opened.
- **Turn usage placement**: the summary row (`turn_usage`) is emitted **immediately before** the final assistant output, not after it — it is process metadata, so it closes out the process records and lets the turn end on the answer. `ChatTurnProjection.AppendCompletedTurn` is the only thing that orders this, and **emission order must equal id order** because persisted history replays with `ORDER BY id`: a bubble the stream already emitted (`_streamedFinalReply`) is therefore *renumbered* when it is moved below the summary, not merely re-added. That renumbering is safe only because `_streamedFinalReply` is always a message this projection created, never a row loaded from the database — if that ever stops being true, the id is a live primary key and reassigning it would orphan the persisted row.
- **Live turn usage**: `ChatTurnProjection` already accumulated the turn's tokens/context/tool-calls for its summary row; `CurrentUsage` publishes that running total mid-turn through `IChatProjectionTarget.ReportUsage`, and `ChatViewModel.LiveUsageText` renders it beside the composer's connection status. Published from the `llm_result` arm only — it is the one arm that moves those numbers, and announcing after every event would push an unchanged value dozens of times a turn. It is the **running total**, not a per-iteration figure (which would flicker and answer a question nobody asks), it **resets per turn** via `OnIsProcessingChanged` (carrying the last turn's total forward would read as the new turn having spent it before it began), and an agent reporting nothing yields `TurnUsage.IsEmpty` → empty string → the slot collapses, because unreported is not the same as zero. The headless persist target ignores the report; the same figures still reach storage through the summary row.
- **Tool timeline rendering** (`Controls/Chat/ToolActivityView.xaml` over `Models/ToolActivity.cs`): one card per turn, one row per tool. A row shows the tool's name, **what it was given**, and what came back. That middle part is `Models/ToolInvocation.cs` — `ToolInvocations.Read(toolName, argumentsJson)` classifies a step into a family (Command / Search / Path / Url / Task / Text) and pulls the shell command, pattern, URL or delegated task out of the arguments, with a two-pass name lookup (exact table, then ordered keyword scan) for exactly the reason `ToolIcons` has one — `remote_bash` and `fs.writeFile` have to reach the same family as `bash` and `write`. **Add a tool family there, not in the view.** Two decisions worth keeping: it is derived at *render* time from the already-persisted `Arguments` (like `IconKind` is from `ToolName`), so it costs no column and conversations recorded before it existed show their commands as soon as they are reopened; and the row's target digest (`ShowDisplayTarget`) and the inline one-liner (`ShowInlineInvocation`) both stand down when the fuller form is on screen, so a grep row never reads "Search: TODO" above a line saying "TODO". A step renders its output as either a monospace log or markdown prose, decided by `ToolInvocations.ProducesMarkdown` — an explicit opt-in list (`load_guide` and friends, plus `write_plan`/`update_plan`, which hand back the plan they just wrote), **never a guess from the content**, because a shell transcript or a stack trace depends on its exact whitespace and a `#` in program output is not a heading; a failed step always takes the log branch for the same reason. Membership is by exact name rather than a keyword: `exit_plan_and_implement` also carries "plan" and its result really is a status report.
  **The collapsed row's invocation preview must be flattened, and `TextWrapping="NoWrap"` does not do that** — NoWrap suppresses *automatic* wrapping, not literal newlines, and ellipsizing applies per line. `ToolInvocation.SingleLineText` collapses whitespace runs and caps the length; `InvocationText` (the collapsed row) binds it, while `InvocationDisplayText` (the expanded block) stays verbatim. Without it a tool whose argument is a whole document unfolded the entire thing across the transcript *when its step was collapsed* — the one state that renders that row.
  Both output blocks' `ScrollViewer`s set **`HorizontalScrollMode="Disabled"`, not just `HorizontalScrollBarVisibility="Disabled"`**: hiding the bar leaves scrolling enabled, which hands the child an unconstrained width, so `TextWrapping.Wrap` silently stops wrapping and long lines and wide tables are clipped with no way to scroll to them. **The same "never guess from the content" rule governs a step's pass/fail status, and it is the sharper trap of the two**: `ToolActivityProjector.Classify` infers Failed/Warning by scanning the result text for words like `failed`, `exception`, `timeout` and bare `403`/`404`, because most tools describe their problems in prose and never set a `status` field. That inference is only valid when the result is the tool *talking about itself*. For a tool that hands back a document — a file read, a guide, a grep listing, a page's text — those words belong to the content, and matching them painted perfectly successful reads red (a system prompt that explains error handling, a log file, any source file containing `catch`). `ToolInvocations.ReturnsContent` is the explicit opt-in list that exempts those tools; for them only the host's own `status` may declare a failure. Writes and deletes are deliberately *not* on it — their result really is a status report. Note its keyword pass uses `(?:^|[^A-Za-z])`, not `\b`: `_` is a word character in .NET regex, so `\bread` finds no boundary in `remote_read_file`. Note the `$` prefix carries **no trailing space** — XAML collapses whitespace between adjacent inlines, so the gap is a panel `Spacing` in the row and `ToolInvocation.DisplayText` in the wrapping block.
- **Process-wide memory bounds**: `AgentConnectionService` caps an incoming WebSocket text frame at 80 MiB (enough for the 50 MiB image limit after base64 expansion), closes oversized frames with `MessageTooBig`, and never retains a receive buffer above 1 MiB after dispatch. Buffered `llm_call`/`llm_result` events retain only projection/usage scalars rather than repeated prompt/provider payloads. `EndpointResolver` prunes expired entries and caps each endpoint/info cache at 128 keys; `ConversationRunRegistry` retains at most 64 terminal snapshots and never retains their raw events; the highlighted-text font metric cache is capped at 32 combinations. Deleting a conversation/agent must also clear its socket-wiring, run snapshot, config, presence, and notification state. `ConversationCache` is bounded by both four entries and an estimated 16 MiB. Because small managed wrappers own much larger native XAML document trees, every eighth fully detached `ChatPage` checks private bytes; only pressure above 320 MiB can schedule an optimized non-blocking Gen2 collection, with a 30-second cooldown. The real-window memory gate defaults to 24 measured cycles, 6 warm-ups, and 750 ms settling, with each scenario in a fresh process.
- **Chat message persistence**: `messages` is one row per rendered bubble (not a serialized envelope), keyed `(conversation_id, id)`. Writes are **incremental** — `ConversationRepository.UpsertMessagesAsync` is the only write path and touches only the rows handed to it (`INSERT ... ON CONFLICT(conversation_id, id) DO UPDATE`, `created_at` left alone on update); each written row's attachments are replaced wholesale by a `message_id`-scoped delete plus re-insert, because an attachment's id is content-derived and an existing agent bubble can gain an image mid-turn. Nothing reads or rewrites the whole conversation on a save, so a turn costs O(turn), not O(conversation). The persist path (`AgentSessionManager.LoadTurnWindowAsync`) therefore loads only what a turn's projection can actually touch: `GetNextMessageIdAsync` (a `SELECT MAX(id)+1`, no rows) plus `LoadLastAgentMessageAsync` — that one row is the seed because an `agent_image` event hangs its attachment on the last agent bubble and the final reply is deduped against it. If you add a projection step that mutates an *older* row, that window is what you have to widen. `ChatMessage` carries generic `Event*` fields (`EventKind`, `EventTitle`, `EventDetail`, `EventArgs`, `EventMeta`, `Status`) reused across very different bubble types (`activity`, `tool_activity`, `ask_user`, `approval`, `plan_review`) — check `EventKind` before assuming what a field means for a given bubble.
- **Stop and mode** (`AgentModes`/`ApprovalRejectModes` in the protocol library; `AgentSessionManager.RequestStopAsync`/`SetModeAsync`). Two facts about the host drive this whole design, and both are counter-intuitive enough to be worth stating before you touch it:
  - **Global Stop is `{"type":"INTERRUPT"}`.** It is fire-and-forget on the active socket: the current tool is allowed to finish and the host stops at the next iteration boundary, so the UI stays in `STOPPING`, blocks new `INPUT`, and waits for `OUTPUT`/`ERROR`. Duplicate INTERRUPT frames are valid and are sent rather than client-deduplicated. An approval card has a separate immediate Stop action: it answers that approval with `{approved:false, mode:"reject_hard", feedback?:...}`, locally settles the run, and restores input without waiting for OUTPUT. Skip and Explain use `reject_soft` and `reject_explain` respectively; never substitute one scope for another based on `_pendingInteractive`.
  - **A `mode_change` frame only reaches the agent while a turn is running** (the host's ws_router forwards non-CONNECT/INPUT frames only when an `active_io` exists) and it is applied at the next iteration boundary. A mode in CONNECT's `session` only survives for a session the host has never run, because `merge_sessions` replaces our session wholesale whenever the server's iteration count is higher — which it always is, since we report none. So **the mode is client-owned state** (`sessions.mode`), and `SendInputAsync` re-asserts it by sending `mode_change` *immediately after* the INPUT, on the same socket, every turn. Reverse direction matters too: the agent can call `enter_plan_mode()` itself, so `mode_changed` is both a typed event and a stream event, and the view model follows it rather than re-asserting the user's last pick. ULW is deliberately unsupported — its checkpoint blocks the agent on `io.receive()` and would hang the turn without a `ULW_RESPONSE` card.
- **Onboarding gates** (`ONBOARD_REQUIRED` → `AgentInteractiveParsers.ParseOnboard` → `OnboardRequest`): the agent's trust gate names what it accepts in `methods` — `invite_code`, `payment`, or both — plus `payment_amount` and sometimes `payment_address`. The card offers only what is on offer, and two rules keep it answerable: **no methods named means offer the invite code** (that is the near-universal gate, and showing nothing would strand the user on a card with no way through), and **a payment gate with no quoted amount is not offered** because there is nothing to act on. `payment_address` is read, never derived — the agent's own address is not a safe stand-in, and an invented destination for a real transfer loses the user's money, so an absent address renders no address block. The payment button is the user *asserting* a transfer already happened (`ONBOARD_SUBMIT` with `payment`); nothing in the client moves money and the agent verifies the claim itself. Unlike `InviteCode`, a payment claim is deliberately **not** stored for auto-resubmission on reconnect — re-asserting it would report a second payment that never happened.
- **Credentials in interactive turns**: an `ask_user` carrying `fields` is a login form, and the password it collects reaches the local database through **two** doors. The wire answer (`InteractiveResponseBuilder.BuildAskUserAnswer`) must stay complete — the agent asked for it because it needs it — but the *summary* is what lands on the resolved card and in the persisted `event_meta` column, so it goes through `BuildAskUserAnswerSummary`, which masks any field whose `type` is `password` **or** whose name looks like a secret (an agent is not obliged to set the type). The second door is the agent typing that password into a browser: those tool arguments are persisted too, and nothing in `{"text":"hunter2"}` names it a secret. `SessionSecrets` (process-wide, in-memory, never persisted) remembers what the user submitted and `ToolActivityProjector.SanitizeText` masks **exact** matches only — a substring rule would turn a short password into a censor that fires on ordinary words. Also note `SanitizeJson` serializes with `UnsafeRelaxedJsonEscaping`: the default encoder escapes `+`, `&`, `<`, `>` and all non-ASCII, which rendered every search URL as `Sydney+weather` and every Chinese argument as `\uXXXX`. That encoder name warns about HTML/JS injection contexts, which this path (XAML `TextBlock`, parameterized SQLite, re-parsed JSON) is not — don't copy it somewhere that is.
- **Interactive turns** (`ask_user`/`approval_needed`/`plan_review`) render as persistent inline chat bubbles with live controls (submit button, approve/reject, etc.), not `ContentDialog` popups — this matches the reference web client's chat-item-feed model and keeps the decision visible in history. Their live *control* state (options/fields/free text) is intentionally **not** persisted to SQLite — once the WebSocket session is gone, answering is meaningless. The *resolved result* is persisted, though: the reply-less event stream can't carry the user's answer, so when the page answers it calls `AgentSessionManager.RecordInteractiveAnswer`, and at turn-persist time `ResolveInteractiveCards` stamps the chosen result onto the re-projected card's `EventMeta`/`Status`. Any interactive card a persisted (terminal) run left unanswered is sealed as `"No selection"` — so reloaded history shows what was chosen (or that nothing was) instead of dead, unanswerable controls.
- **Multimodal attachments**: outgoing images/files are picked via `AttachmentPickerService` (`FileOpenPicker`, HWND resolved through the static `App.MainWindow` since `ChatComposer` is a `UserControl` with no HWND of its own) and preflight-validated via `AttachmentValidationService` against the agent's real `/info` capability (client-side checks are a UX nicety — the server remains the final authority). Pending drafts and retry state retain only local file descriptors. `AttachmentEncoder` reads aligned pooled chunks and creates the base64 data URL immediately before INPUT; the executor releases encoded lists as soon as the UTF-8 frame is sent rather than pinning them for the whole turn. Incoming `agent_image` events are decoded/downloaded and cached to disk via `AttachmentImageCacheService` *before* ever touching `ChatMessage` or SQLite — the message list and DB only ever hold a local cache path plus metadata, never a base64 payload. Wire contract specifics (exactly what `images`/`files` look like on `INPUT`, what `agent_image`/`files_received` look like coming back, and what is/isn't actually enforced server-side) live in the `ConnectOnion.Protocol` doc comments above, not duplicated here — read `AttachmentModels.cs` and `InputMessageBuilder.cs` before changing this path.
- **Agent skills** (`Services/AgentSkills.cs` in `Core`, over `EndpointResolver.ParseSkillsFromInfoJson`): an agent's `/info` declares `skills`, and two surfaces consume them. The composer opens a **slash palette** while the draft is a `/`-command still being typed — `AgentSkills.TryGetSlashQuery` says when that is, and **the space is the commit**: past it the palette closes and Enter goes back to sending, which is what stops a completed command's arguments from being swallowed. Matching is deliberately forgiving and ranked prefix → substring → in-order letters, so `/linkedeng` finds `linkedin-engagement`; `OrderBy` is stable so equal-ranked skills keep the agent's declared order and the highlighted row does not move under the user's arrow keys between keystrokes. The agent-detail page turns the best few skills into **opening chips** (`AgentSkills.BestOffers`) — internal/debug skills are dropped from the chip row only (they stay in the palette, where typing the name means it), descriptions that will not cut into a clean short offer yield null rather than a truncated one, and an agent with no usable descriptions falls back to the composer's three generic starters. `ShowSuggestions` is on for `AgentDetailPage` and off for `ChatPage`: chips answer "what do I even ask this thing", which is only a question before the conversation starts. Both view models read skills from the same cached `/info` as `AcceptedInputs`, so neither costs an extra round trip.
- **Drag-and-drop attachments**: `Controls/Chat/ChatComposer` is the only real drop target — `AttachmentDropService` (the drop counterpart to `AttachmentPickerService`) classifies dropped `StorageFile`s by extension (no file-type filter like the picker gets) into `PendingAttachment` drafts, which still flow through the same `AttachmentValidationService`/`AttachmentEncoder` pipeline; dropped folders are skipped silently rather than recursively expanded. `Shell/MainWindow.DragDrop.cs` only paints a window-wide "drop it on the composer" hint (`RootGrid.AllowDrop` + handlers registered with `handledEventsToo: true` so the hint still updates after the composer's own drag handlers mark the event `Handled`) — it is not itself a drop target.
- **Global find overlay** (Ctrl+F, `Shell/MainWindow.ViewMenu.cs`): pages that support in-content search implement `Views.IFindHost` (`OpenFind`/`CloseFind`/`SetFindQuery`/`SelectNextFindMatch`/`SelectPreviousFindMatch`, plus a `FindStateChanged` event); `MainWindow` attaches to whatever `ContentFrame.Content` currently is and drives one shared find UI (`FindOverlayPanel`/`FindTextBox`) against it — add `IFindHost` to a new page rather than building a page-local find UI.
- **Keyboard shortcuts are data, not literals.** `Services/KeyboardShortcutCatalog` (in `Core`) is the single source of truth for every shortcut the app advertises; adding a customizable entry there is what makes it real, and there is no second place to edit. Entries split two ways: the **customizable** 15 are the ones the app dispatches itself (`Shell/MainWindow.FileMenu.cs`/`ViewMenu.cs`/`ChatShortcuts.cs`/`HelpMenu.cs`), and the **non-customizable** rest are listed only so the shortcuts dialog stays complete — the app doesn't own their key (a `TextBox` handles Ctrl+C natively; the composer's Enter is the Enter-key preference; Esc belongs to whatever has focus) and each carries a reason string saying so. `KeyboardShortcutService` (singleton) resolves catalog default + user override into the live chord and answers the handlers' `IsShortcut(id, keyCode, ctrl, shift, alt)` question, so **handlers never compare key codes themselves**. Overrides persist as canonical strings (`"Ctrl+Shift+N"`) in `preferences.shortcut_overrides_json` — a pre-existing baseline column shared with the unrelated `composer.enterKey` entry, which the service is careful to leave alone. Several deliberate behaviors worth not "fixing": a rebind onto a chord another action holds is **refused**, not stolen (a silently-dead shortcut is unnoticeable); rebinding back to the factory chord **deletes** the override row rather than pinning it, so a future default change still reaches that user; an override that no longer parses falls back to its default rather than leaving the action unfireable; and `Rebuild` seeds defaults first and resolves collisions by catalog order, so a colliding stored pair loses deterministically instead of by dictionary iteration order. `KeyChord` holds a **raw Win32 virtual-key code**, not `VirtualKey`, purely so it stays WinRT-free and headlessly testable. `Shell/MainWindow.Shortcuts.cs` pushes live chords into `KeyboardAcceleratorTextOverride` on the 14 menu items (subscribing to `BindingsChanged`, hopping to the UI thread — the service saves on a background task), because a XAML literal would advertise a combination that no longer fires; the fifteenth customizable action is the composer mode shortcut and has no menu item. `StartupStateService` loads shortcut overrides with the other startup preferences; until it completes the service answers with catalog defaults, so a keystroke during startup still works.
- **Sidebar** (`Controls/Shell/ShellSidebar.xaml[.cs]`): a **single** `ItemsRepeater` over one flat, heterogeneous row list (`SidebarRows`), dispatched by `Common/ShellSidebarRowTemplateSelector` into five templates — pinned header, pinned conversation, agent, time-group label, conversation. **It was three nested repeaters inside a `StackPanel`, and nothing in the sidebar virtualized.** `ItemsRepeater` virtualizes against the nearest scrolling surface, and both an outer repeater's item container and a `StackPanel` measure their children with an unconstrained height — so every conversation of every expanded agent was fully realized however far off screen, each carrying its own inline `ResourceDictionary` of six brushes. Flat is what gives the tree a real viewport. The selector dispatches on row **type** specifically so every template kept its `x:DataType` and every `x:Bind` inside it: flattening changed the list's shape without touching a binding. The one case type cannot separate is a conversation appearing both as a pinned shortcut and under its agent — same class, two rows — hence `ShellSessionItem.IsPinnedRow`. **The consequence for the code-behind is that expansion is a list rebuild, not a `Visibility` flip**: a collapsed agent's rows are absent, not hidden (hidden rows would still be realized, which is the whole point). `RebuildSidebarRows` is the single funnel and every `IsExpanded` write must go through it — `RefreshAsync`, both disclosure handlers, and `RevealAgentInSidebar`. **Conversations are fetched per agent and only for expanded ones** (`SessionPageSize` = 25, a "show more" row ending any branch with older conversations): a collapsed branch costs nothing, which is where most of the saving is, since the whole index used to be read regardless of what the user could see. Three things about that are easy to get wrong and are handled explicitly — a refresh reloads *as many pages as a branch had* (`LoadedPages`), or an incoming message would silently collapse a branch the user had paged deep; `EnsureActiveSessionVisibleAsync` splices the on-screen conversation in when it falls outside the loaded page, or opening a conversation far down a long branch draws it with nothing selected; and the incremental page loads pass `prune: false` to `RefreshSessionPreviewCacheAsync`, because that method evicts everything outside the list it is given and an incremental load only knows about the page that just arrived. `ShellAgents`/`PinnedSessions` remain the tree the rest of the class reasons about (lookups, presence, selection repaint); they are just no longer what XAML binds to. Row hover and selection are unified through one `RowStateToBackgroundConverter`-driven Border per row (bound to a computed `ShowRowBackground = IsSelected || IsHovered`) rather than each sub-button showing its own independent hover — sub-button chrome is neutralized via a `Resources` dictionary declared **inline on each row's container element**, not shared through a `StaticResource` (WinUI requires a `ResourceDictionary` assigned to `FrameworkElement.Resources` to be uniquely owned per element; a shared instance throws `XamlParseException` the moment a second row tries to reuse it). The row templates live in `Grid.Resources` **after** `ShellNavButtonStyle`, and both facts are load-bearing: `StaticResource` resolves upward from where a template is *declared* (so `UserControl.Resources` could not see that style) and requires forward declaration within one dictionary, while the `Click`/`PointerEntered` handlers resolve against the code-behind of the file the template is written in.
  - **Keyboard reachability is the constraint that shapes each row.** `ItemsRepeater` gives no arrow-key navigation of its own (unlike `ListView`), so the tree carries `XYFocusKeyboardNavigation="Enabled"` for Up/Down traversal on top of the Tab order — and every tab stop per row has to earn its place, because they multiply by the number of agents and conversations on screen. The avatar button and the name button fire the identical `Agent_Click` with the same `Tag`: the avatar is a pointer target only (`IsTabStop="False"`, `AccessibilityView="Raw"`), because as a second focus stop it did exactly what the next one did. Don't add a focusable control to a row template without checking what it costs a keyboard user with the tree expanded.
- **Color system** (`Styles/Colors.xaml` + `Styles/Brushes.xaml`, merged into `App.xaml` after `XamlControlsResources`): the single source of truth for every color in the app — a Deep Purple brand palette expanded into semantic Light/Dark tokens (`BrandPrimaryBrush`, `SurfaceElevatedBrush`, `TextSecondaryBrush`, `SidebarItemSelectedBrush`, `SearchMatchBackgroundBrush`, `UserMessageBackgroundBrush`, ...). `Colors.xaml` holds raw `Color` resources per theme; `Brushes.xaml` wraps them as `SolidColorBrush`es pages actually bind to via `{ThemeResource ...}`, **and** re-points WinUI's own themed keys (`TextFillColorSecondaryBrush`, `CardBackgroundFillColorDefaultBrush`, `AccentFillColorDefaultBrush`, `ButtonBackgroundPointerOver`/`Pressed`, `FocusVisualPrimaryBrush`, ...) at the same tokens so native Fluent chrome (Expander, default Button hover, hyperlinks) stays visually consistent without replacing any `ControlTemplate` — `ToggleSwitch`/`CheckBox`/`RadioButton` are deliberately left alone. Code-behind that needs a raw `Windows.UI.Color` (`AppWindowTitleBar` in `MainWindow.xaml.cs`) goes through `ThemeService.GetColor(key, isDark)` rather than duplicating hex literals; the composer's waveform deliberately uses ordinary XAML shapes and brushes, not a Win2D `CanvasAnimatedControl`, because constructing one per chat page creates a native swap chain and render-thread pool before recording even starts. Anything reading a `Brush` by string key (converters, `HighlightedTextBlock`, `WinUiMarkdownRenderer`) goes through `Common/ThemeBrushResolver`, which **caches by key and clears the cache from `ThemeService.ThemeApplied`** — so a live theme flip still never leaves stale colors on screen, without paying a merged-dictionary lookup per converter call (these run once per bound property per row, on every container recycle, which is tens of lookups per frame while scrolling). Do not re-add a direct `Application.Current.Resources[key]` read in a converter, and do not cache a brush anywhere that does *not* observe `ThemeApplied`: `PublishTheme` is the single funnel that raises it, covering both the explicit picker and following the system theme, and `RenderHotPathContractTests` pins that. A handful of pre-existing resource keys (`ShellBackgroundBrush`, `ComposerBackgroundBrush`, `StatusSuccessTextBrush`, ...) are kept as redirects onto the new tokens for source compatibility — prefer the new semantic names in new code.
- **CommunityToolkit.WinUI (UI)**: two toolkit packages back UI presentation. `CommunityToolkit.WinUI.Animations` drives entrance/exit motion on discrete surfaces — the in-app toast cards (`InAppNotificationHost` sets `Implicit.SetShowAnimations` for entry and plays an `AnimationBuilder` fade/slide on `Remove` before dropping the card, guarded by a `_dismissing` set so the auto-dismiss timer can't race the close button) and the `OfflineNoticeBar` (`Implicit.ShowAnimations` declared inline in `ChatPage.xaml`/`AgentDetailPage.xaml`). Keep animation to self-contained, non-virtualized elements — don't attach implicit animations to `ItemsRepeater`/`ListView` item roots, which fights recycling. `CommunityToolkit.WinUI.Controls.SettingsControls` provides `SettingsCard`: `SettingsPage.xaml` is the flattened Windows 11 pattern — a section-header `TextBlock` over stacked `SettingsCard`s (`Header`/`Description` + the control as content), not the old hand-rolled `SettingRow` inside a section card (removed). The cards inherit the app palette because `Brushes.xaml` already re-points the Fluent `CardBackgroundFillColorDefaultBrush`/`…Border…` keys the toolkit's default style reads.

- **Logging** is **Serilog**, configured in the `App` constructor and bridged into DI (`AddSerilog`), so injected types keep using plain `ILogger<T>`. It writes rolling daily files to `AppStorage.LogsDir` (10 MB cap, 14 retained) — that is `<data root>\logs`, so logs follow the database rather than living at a fixed path: `%AppData%\ConnectOnion\logs` unpackaged, `LocalState\ConnectOnion\logs` packaged, and inside the override when `CONNECTONION_DATA_ROOT` is set. The file sink sits **behind `WriteTo.Async`**, because a log call otherwise runs a synchronous disk write on whatever thread logged — including the UI thread — and `shared: true` adds a cross-process mutex to each one. `shared` itself is load-bearing and stays: toast activation launches a short-lived second process that writes the same file. The trade is that a hard crash can lose what is still queued, which is acceptable only because `ShutdownAsync` ends on `Log.CloseAndFlushAsync()`; keep it that way rather than reaching for `blockWhenFull`, which would put the UI thread back on the disk. The `Microsoft`, `System.Net.Http`, and `Polly` categories are pinned to `Warning` on purpose: `HttpClient` logs four lines per request and the resilience pipeline one per attempt, so every presence-probe sweep wrote ~30 lines of framework chatter and buried the app's own events. At `Warning` the interesting half — a retry that actually fired — still lands. Shutdown is `App.ShutdownAsync` (idempotent via `Interlocked`, called from `MainWindow.Closed`): it drains the run manager and stops the Generic Host under bounded timeouts, logging each phase's duration, then flushes Serilog last.
  - **There are three ways to reach that logger and no fourth**, because the two obstacles are real: `Core` cannot reference Serilog, and WinUI constructs its own pages and controls. Container-created types (services, repositories, view models) take `ILogger<T>` as a **constructor parameter** — the repositories declare it optional with a `NullLogger` fallback so a test can still `new` them. A `static` entry point in `Core` gets a **facade with a `Configure(ILoggerFactory)`** that no-ops until `App` wires it up; `NotificationLog` and `IdentityStore` are the two, both configured together in the `App` constructor. Framework-created **code-behind** goes through `AppServices.Logging.CreateLogger<T>()`, the same DI boundary the rest of `AppServices` exists for.
  - **CA1848 is on**, so every call site is a pre-compiled `LoggerMessage.Define` delegate, never `logger.LogWarning(…)`.
  - **`Debug.WriteLine` is never a failure path's only record.** It carries `[Conditional("DEBUG")]`, so a Release build compiles it away entirely — a `catch` whose sole trace is a `Debug` line is silent exactly where it matters. Use it only *alongside* a real logger call for attached-debugger convenience (`ConversationRepository.LogFailure` is the pattern), or for development tracing nobody would want in a shipped log file (`AgentSessionManager.DebugRunLogger` writes a line per run phase — deliberately debugger-only, for the same reason the framework categories are pinned to `Warning`). Do not log successful steps at all: a working attachment or a rendered avatar reports itself on screen.
- **Localization** covers two locales: `Strings/en-US/Resources.resw` and `Strings/zh-CN/Resources.resw`, which must stay key-for-key identical. Views reference resources by `x:Uid`. **Keep the fallback text in the XAML when you add a `x:Uid`** — it's what keeps a development build diagnosable when a resource is missing. Strings that only exist at runtime (a message picked from an error code, say) can't use `x:Uid`, so they go through `Common/LocalizedStrings.Get(key, fallback)`, which takes the English text as a parameter for the same reason: `ResourceMap` throws on a missing key and `TryGetValue` returns null, either of which would turn a forgotten resw entry into a blank dialog in the one path nobody exercises.
  - **`Core` gets its wording from `Common/CoreStrings`, and this is the half that is easy to miss.** Core computes a large amount of XAML-bound display text as computed properties — the approval card's title/subtitle/risk lines, the activity card's header, the interactive phase labels and descriptions, the diff card, tool status, usage ranges — with no `x:Uid` to check and no assignment statement to pattern-match, which is how ~70 English strings once sat outside every gate. Core cannot hold a `ResourceManager` (Windows App SDK, which the ArchUnit layer gate excludes), so `CoreStrings` is a facade that returns its English fallback until `App`'s constructor calls `CoreStrings.Configure(LocalizedStrings.Get)`. `Architecture/CoreLocalizationTests` is the gate: display text must route through it, every key must exist in both locales, and `App` must wire it up.
  - **The line between display text and a marker is the thing to get right here.** A great many of these properties are `switch`es whose *left* side is a wire value the host sent (`"Yes, apply this change"`) or a marker this client persisted and later matches on (`InteractiveOutcome`, `EventMeta`'s `"Skipped"`/`"Answered:"`, `EventTitle`'s `"Thinking"`). Those stay English — localizing them makes a translated build fail to recognise rows it wrote itself. Only the right side is localized. Where one property was doing both jobs, it was split: `InteractiveOutcome` remains the marker and `InteractiveOutcomeText` is what XAML binds. `CoreLocalizationTests.AllowedEnglishLiterals` is the explicit list of what may stay English, and adding to it should mean "this is a wire value or a stored marker", never "this one was awkward".
  - `Architecture/LocalizationResourceTests` is the gate, and it checks three separate things because each catches a different silent failure: the two locales hold the **same keys** with non-empty values; user-visible literal text **has an `x:Uid`**; and every `x:Uid`-backed attribute **has its `<Uid>.<Property>` row in both locales**. That last one is the subtle one — an element with a uid but no resource row looks localized from either side alone and just renders its English fallback forever. The surviving deliberately-unlocalized literals are three Segoe glyph codepoints and three instances of the product name.
  - **`AutomationProperties.Name` is user-visible text** and is localized like any other — it is what a screen reader speaks for every icon-only button, and it is the single largest category of keys here. It is checked by the resource-row test but *not* by the uid-presence test, because many are bound to a view model rather than written as a literal.
  - Switching language **requires a restart**, and that is a framework constraint rather than an omission: WinUI resolves `x:Uid` once when a page is constructed, so unlike a `ThemeResource` flip there is nothing to re-resolve on a live tree. `SettingsPage` therefore offers a "Restart now" button that goes through `AppInstance.Restart` — a plain `Process.Start` would be caught by the single-instance redirection in `Program`.

### WinUI/XAML gotchas already paid for in this codebase

Worth knowing before you re-discover them via a build or runtime failure:

- A type referenced from an `x:Bind` `DataTemplate` needs plain `{ get; set; }` properties — `required` or `init` accessors break the compiler-generated `XamlTypeInfo.g.cs` reflection metadata with a confusing `CS9035`/`CS8852`.
- `FluentIcons.WinUI`'s `IconSize` enum only has specific values (`Size10/12/16/20/24/28/32/48`, no `Size14` etc.) — check the actual enum rather than guessing a round number.
- **`IconSize` picks a *font file*, and the small ones are not complete.** Each size is a separate `FluentSystemIcons-Size<N>.otf`, and `Size12` ships **439** glyphs against `Size16`'s 4372 — so `IconSize="Size12"` on an icon with no 12px glyph renders as `.notdef` (a blank or a box), silently, with no build error. `Copy`, `Live`, `Settings`, `Stop`, `Send`, `Image`, `Document`, `MoreHorizontal`, `Mic`, `Folder`, `Key`, and `Wrench` are all missing at 12; `Dismiss`, `ChevronUp`/`Down`, `Chat`, `Pin`, `Add`, `ArrowClockwise`, `Edit`, `Clock`, `Checkmark`, `Warning`, `Info`, `Search`, `Attach`, `Delete`, `Person`, `Bot` are present. The fix is the repo's existing idiom: request `Size16` and shrink it with `RenderTransformOrigin="0.5,0.5"` + `<ScaleTransform ScaleX="0.75" ScaleY="0.75"/>` (12/16) — see `ChatPage.xaml`'s copy buttons and the `Stop` icon beside them. Note a `RenderTransform` doesn't shrink the *layout* slot, so the icon still measures 16px; that's fine inside the 24px action buttons but check the spacing anywhere tighter. **Apply the treatment to every icon in a row, not just the missing one** — the Size12 designs carry visibly heavier strokes than a scaled-down Size16, so a row mixing the two looks wrong in both weight and spacing (this is what the chat message action rows had to be fixed for). To confirm coverage for a new icon, dump the font's glyph order rather than guessing:
  ```bash
  python -c "from fontTools.ttLib import TTFont; print('copy.regular' in TTFont(r'%USERPROFILE%\.nuget\packages\fluenticons.winui\2.2.333\contentTransitive\FluentIcons.WinUI\Assets\FluentSystemIcons-Size12.otf').getGlyphOrder())"
  ```
  (glyph names are the icon's PascalCase name in `snake_case` plus `.regular`/`.filled`).
- `Microsoft.UI.Xaml.EventTrigger` has no `RoutedEvent` property (that's WPF-only); it always fires on `Loaded` implicitly. A XAML-declared `Loaded`-triggered `Storyboard` needs `<EventTrigger>` with no `RoutedEvent` attribute, or just start the `Storyboard` from a code-behind `Loaded` handler — the latter is what this repo uses for the sidebar's online-status breathing animation.
- `Style` setters can't target `Resources` (not a `DependencyProperty`); scope resource overrides by declaring them inline on the actual element instance instead.
- **`x:Load="False"` does not work for `MainWindow.xaml`'s children, and fails silently.** Deferring the three modal overlays was tried (they are invisible at launch and `SettingsOverlay` drags in the whole `SettingsPage`): `FindName(name)` returns **null** from both `RootGrid` and the element's direct parent panel, so the `x:Name`-generated field stays null, the realization helper NREs, and the button that should open the dialog just does nothing. `MainWindow` is a `Window`, not a `FrameworkElement`, so it has no `FindName` of its own and the content root's namescope does not resolve the deferred elements. Measured payoff before it was reverted was ~9 MB of working set and **zero** launch-time change — see `docs/PERFORMANCE.md`. Don't re-attempt without a working realization path.
- **A `UserControl` produces no automation peer of its own**, so an `AutomationProperties.AutomationId` written in its XAML is never exposed to UIA and `ByAutomationId` returns null — and a screen reader gets no dialog boundary either. The five shell overlays (`SettingsOverlay`, `AboutOverlay`, `KeyboardShortcutsDialog`, `AddAgentForm`, `SessionSearchOverlay`) each override `OnCreateAutomationPeer` to return a `Controls/Primitives/ModalOverlayAutomationPeer`, which reports `AutomationControlType.Window` (UIA's control type for a dialog — there is no separate Dialog type). **A new full-window overlay needs the same override**, or it is invisible to both UI tests and assistive tech. Also expect a transient `COMException` (`E_UNEXPECTED`, "Catastrophic failure") from `FindFirst` while the visual tree is mutating; it means "ask again", so poll rather than fail.
- **Automation locators are a source-level contract, not a per-test afterthought.** App XAML currently declares 145 unique `AutomationId`s. Every interactive element with an `x:Name` must also expose an `AutomationProperties.AutomationId`; `AutomationContractTests.Xaml_NamedInteractiveControls_HaveAutomationIds` scans buttons, inputs, selectors, lists, switches and menu items and fails CI when one is missing. Repeated item-template controls may use a stable role ID and be scoped through their identified list/container; the 53 IDs used by the real-window shell suite remain an explicit critical subset in the same test.
- **Typography uses the seven-step compact product ramp in `Styles/Typography.xaml`.** The 139 former page/control literals now reference `ProductMicroFontSize` through `ProductHeroFontSize`; dynamic message/card sizes remain `x:Bind` values. `TypographyContractTests` rejects a numeric `FontSize="N"` anywhere outside the central dictionary. This is the maintainability half only: accessibility scaling still comes from `TextScaleService` and `EffectiveContentScale`, because WinUI 3 does not implement `IsTextScaleFactorEnabled`.
- **These overlays are not `ContentDialog`s, so nothing traps focus in them for free.** Keyboard shortcuts are blocked by `IsModalOverlayOpen`, but Tab used to walk straight out of the "modal" into the page and menu bar behind it. `MainWindow.Overlays.UpdateModalFocusScope` takes the background out of the Tab order while any overlay is up. Two things about the mechanism: it is driven by a `RegisterPropertyChangedCallback` on `Visibility` (every overlay defines `IsOpen` as `Visibility == Visible`, and several close *themselves* without telling the window), and it is applied per-`Control` in `BackgroundFocusRoots()` rather than to `MainContentArea`/`TitleBarArea` — those are plain `Grid`s, and `IsTabStop` exists only on `Control`. `TabFocusNavigation="Once"` alone still admits one tab stop; it is the pair with `IsTabStop=false` that skips a subtree.
- **The dispatcher keeps pumping after `Window.Closed`.** Anything still armed when the window closes — a `DispatcherTimer` tick, an `async void` continuation resuming after an awaited animation — can therefore run against a visual tree the framework is already tearing down. That surfaces as an access violation (`0xC0000005`) **inside `Microsoft.UI.Xaml.dll`**, which is native: no managed `catch` sees it, the log shows a clean shutdown a few hundred ms earlier, and under Visual Studio the debugger has usually detached by then, so Windows invokes the JIT debugger ("choose a Visual Studio version") instead of breaking. If you ever see that dialog on exit, check the Windows Application event log for the faulting module before assuming it's your code. It's a race — it reproduces intermittently and only when something was genuinely in flight.
  - `MainWindow.DetachWindowServices()` (called from `Closed`, idempotent via `Interlocked`) is where the window's own actives get disarmed **synchronously**: it stops the zoom popup's idle timer (`DetachViewMenu`) and calls `InAppNotificationHost.Shutdown()`, which stops every toast card's auto-dismiss timer and clears the stack without animating. A new window-owned timer or animation belongs in that method too. It also asks the current page to disarm itself via `Views.IShutdownDisarmable` — pages stop their timers in `Unloaded`, which is **not** guaranteed to fire on window close, so a page owning a timer (as `ChatPage` does: find debounce, thinking ticker, `ChatComposer.Dispose()`) must implement that interface rather than rely on `Unloaded`. Note the real exit funnel is `MainWindow.ExitApplication` — clicking the title-bar X only shows the "Minimize to tray / Exit" dialog, and minimizing never closes the window at all, so teardown races only exist on the Exit branch.
  - An `async void` handler that touches the tree after an `await` needs an explicit "did we shut down?" check on the far side of it — see `InAppNotificationHost.Remove`, where the exit animation's continuation would otherwise re-enter a cleared stack.
  - Page- and control-owned timers (`ChatPage._findDebounceTimer`, `ChatComposer._recordingElapsedTimer`) stop in their own `Unloaded` handlers, which covers navigation. But `Unloaded` is **not** guaranteed to fire on window close, so don't rely on it as the only disarm path for anything that would be expensive to get wrong.

## Git conventions

Conventional Commits, enforced by convention rather than tooling: `<type>(<scope>): <summary>` (types: `feat`/`fix`/`docs`/`test`/`refactor`/`style`/`chore`/`build`/`ci`; recommended scopes include `chat`, `agent`, `sessions`, `storage`, `settings`, `files`, `ui`, `ci`, `build` — see `docs/GIT_COMMIT_CONVENTION.md` for the full list). PRs use the same format for their title.
